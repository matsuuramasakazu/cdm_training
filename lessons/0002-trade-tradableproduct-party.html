Trade / TradableProduct / TradeLot の構造と、当事者（Party ↔ Counterparty）の抽象化メカニズム

Lesson 0001 で鳥瞰した6階層のうち、実務データの項目が最も集中する L5（Trade と TradableProduct）にズームインします。なぜCDMはプロダクト定義の中に具体的な銀行名（LEI）を直接書かず、Party1 / Party2 という抽象ロールを経由させるのか？その設計理由とJSON参照の追跡方法を一次ソースから完全習得します。

🎯 このレッスンの到達ゴール（Missionへの接続）

為替フォワードや為替オプションの実データJSONを読んだとき、「実際にどの銀行（LEI）がどの通貨を支払い、どちらがオプションの買い手なのか」を PayerReceiver / BuyerSeller → Counterparty → Party の参照チェーン（@ref:external → @key:external）から100%正確に特定・設計できるようになります。

1. Trade extends TradableProduct：2つのクラスの役割分担

Lesson 0001 で確認した通り、Trade 型（event-common-type.rosetta:L295）は TradableProduct 型（product-template-type.rosetta:L321）を継承（extends）しています。なぜ最初から1つの型にまとめず、親子に分けているのでしょうか？

理由は「約定前の見積・注文・執行指示（Pre-execution / Execution）」と「約定成立後の取引契約（Trade）」で、経済条件の部分をそのまま再利用するためです。両者の属性の分担は以下の通り明確に分かれています。

2. 当事者抽象化の核心：なぜ Party1 と party1 を分けるのか？

実務でCDMのJSONデータを初めて読む人がほぼ確実につまずく「罠」があります。公式の検証済みサンプルデータ execution-fx-forward-func-output.json:L252-L301（および fx-ex03-fx-fwd.json）の当事者定義を見てみましょう。

⚠️ 公式サンプル JSON における「Party1 ↔ party2」の交差マッピング（execution-fx-forward-func-output.json:L173-L176, L252-L301） 
// ① Product 内（SettlementPayout）：誰が原資産（10,000,000 EUR）を支払うか？
"payerReceiver" : {
  "payer" : "Party1",
  "receiver" : "Party2"
},

// ② TradableProduct 直下（counterparty）：抽象ロール Party1 / Party2 と実体キーの対応付け
"counterparty" : [ {
  "role" : "Party1",
  "partyReference" : { "@ref:external" : "party2" }  // ← Party1 の中身は "party2"！
}, {
  "role" : "Party2",
  "partyReference" : { "@ref:external" : "party1" }  // ← Party2 の中身は "party1"！
} ],

// ③ Trade 直下（party）：実在する金融機関（LEI）の定義
"party" : [ {
  "@key:external" : "party1",
  "partyId" : [ {
    "identifier" : { "@data" : "BFXS5XCH7N0Y05NIXW11" }, // ABN Amro
    "identifierType" : "LEI"
  } ]
}, {
  "@key:external" : "party2",
  "partyId" : [ {
    "identifier" : { "@data" : "213800QILIUD4ROSUO03" }, // Deutsche Bank (DB)
    "identifierType" : "LEI"
  } ]
} ]

注目してください。counterparty 配列の中で、抽象ロール "Party1"（大文字Pの列挙値）は "@ref:external": "party2"（ドイツ銀行）を指し、"Party2" は "@ref:external": "party1"（ABNアムロ）を指しています。もし開発者が「Party1 だから party1 のことだろう」と決め打ちすると、1,000万ユーロの支払人と受取人が完全に逆転してしまいます。

なぜCDMはこのような3段階の間接参照（Indirection）を採用しているのか？

  • 理由① 商品の再利用性と標準化（Product Agnosticism）：
    NonTransferableProduct（経済条件）の中に特定の銀行のLEIを書かないことで、「EUR/USDのフォワード契約」「EUR/USDのバニラオプション契約」というプロダクト構造を当事者から完全に独立（Party-agnostic）させています（base-staticdata-party-type.rosetta:L7）。
  • 理由② ノベーション（更改：PartyChange）時の不変性：
    取引の途中で一方の当事者（たとえばドイツ銀行）が別の銀行へ契約を譲渡（Novation）する場合、CDMの関数 Create_PartyChange（event-common-func.rosetta:L897-L958）は、外側の Trade -> party と counterparty の参照先だけを新しい銀行に差し替えます。内側の Product（EconomicTerms や Payout）には1ビットも変更を加える必要がありません。

C1: Trade と ExecutionDetails / ContractDetails

Trade は親 TradableProduct の属性に加え、約定成立後の管理に必要な8つの属性を持ちます。

  • tradeIdentifier (1..*)：必須（1個以上）。両当事者それぞれの社内取引番号や、規制報告用の UniqueTransactionIdentifier (UTI) / UniqueSwapIdentifier (USI) を格納します。
  • tradeDate (1..1)：必須。取引が合意された約定日（[metadata id] 付き）。
  • party (0..*)：取引に関わる当事者（LEI等）の実体リスト。
  • partyRole (0..*)：執行ブローカー、清算機関、ヘッジ当事者などの追加ロール。
  • executionDetails (0..1)：執行形態（Electronic / Voice 等）、執行市場（executionVenue）、パッケージ取引参照（packageReference）。condition ExecutionVenue により、電子執行（Electronic）の場合は executionVenue が必須となります。
  • contractDetails (0..1)：準拠法（governingLaw）やISDAマスター契約（documentation）。

    party Party (0..*)

C2: TradableProduct と TradeLot（ロット分割と複数レッグ）

TradableProduct は、商品テンプレート product (1..1) とロット配列 tradeLot (1..*)、そして2者の対応 counterparty (2..2) を持ちます。

  • なぜ tradeLot (1..*) と priceQuantity (1..*) の2段階配列なのか？
    • 外側の tradeLot (1..*)：同じ契約に対して後から増額（Increase）や追加ロット取引を行った際、別ロット（lotIdentifier 付き）として追加できるようにするためです。通常の単一約定の為替取引では tradeLot は要素数1 です。
    • 内側の priceQuantity (1..*)：1つの商品の中に複数のレッグ（例：FX Swap の Near Leg と Far Leg）がある場合、1つの TradeLot の中に2つの PriceQuantity 要素を並べて表現します（Lesson 0003〜0004で詳解）。
common-domain-model/rosetta-source/src/main/rosetta/product-template-type.rosetta (L317-L330) 
type TradeLot: <"Specifies the price and quantity of a trade lot...">
    lotIdentifier Identifier (0..*) <"Specifies one or more identifiers for the lot, if any.">
    priceQuantity PriceQuantity (1..*) <"Specifies the settlement characteristics of a trade lot: price, quantity, observable (optionally)... This attribute has a multiple cardinality to allow to specify the price, quantity and observable of different legs in a single, composite product (e.g. a Swap).">

type TradableProduct:
    product NonTransferableProduct (1..1) <"The underlying product to be included in a contract or execution.">
    tradeLot TradeLot (1..*) <"Specifies the price, quantity and effective date of each trade lot...">
    counterparty Counterparty (2..2) <"Specifies the parties which are the two counterparties to the transaction.">
    ancillaryParty AncillaryParty (0..*) <"Specifies the parties with ancillary roles in the transaction.">
    adjustment NotionalAdjustmentEnum (0..1)
FX Forward（1要素）vs FX Swap（Near/Far の2要素）の tradeLot 構造比較

    "quantity" : { "@key:scoped" : "quantity-1", "value" : 10000000, ... },

C3: Party と TradeIdentifier（@key:external による参照基盤）

Party 型には [metadata key] が付与されており、JSON上では "@key:external": "party1" のようなドキュメント内キーを持ちます。

  • Party の識別子（partyId (1..*)）：PartyIdentifierTypeEnum により LEI（20桁の取引主体識別子）、BIC（SWIFTコード）、MIC（市場識別コード）等を明示できます。
  • TradeIdentifier の発行者（condition IssuerChoice）：取引番号を誰が発番したかを表す際、issuerReference Party (0..1)（@ref:external で party を参照）または issuer string (0..1)（文字列で直接記述）のどちらか一方を必須選択（required choice）します。

C4: Counterparty と AncillaryParty（抽象ロールと実体のブリッジ）

Product 内部の抽象ロールと、外側の Party 実体を結ぶブリッジが以下の2つの型です。

  • 主たる2当事者：counterparty Counterparty (2..2)
    カーディナリティが (2..2) であるため、必ず Party1 と Party2 の2要素が存在します。CDM内部の関数 ExtractCounterpartyByRole（base-staticdata-party-func.rosetta:L4-L15）がこの配列を検索して実当事者を特定します。
  • 付随ロール当事者：ancillaryParty AncillaryParty (0..*)
    独立計算代理人（CalculationAgentIndependent）や、オプションの手動権利行使通知の受取先（ExerciseNoticeReceiverPartyManual）など、Product 内で指定された AncillaryRoleEnum を実際の Party に紐づけます。TradableProduct の多数の condition（L344-L394）により、Product 側で該当ロールを使った場合は ancillaryParty 側にも必ず登録することが強制されています。
base-staticdata-party-type.rosetta (L7-L16) & product-template-type.rosetta (L352-L356, L376-L380) 
type Counterparty:
    role CounterpartyRoleEnum (1..1) <"Either Party1 or Party2">

type AncillaryParty:

C5: 方向を表す3つの型：PayerReceiver / BuyerSeller / PartyReferencePayerReceiver

「誰が誰に支払うか／誰が買い手か」を表す型は、配置される場所（Productの内か外か）と商品の種類によって以下の3つが厳密に使い分けられます。

  • ① PayerReceiver（Product 内のすべての PayoutBase）：
    payer と receiver を CounterpartyRoleEnum（Party1 / Party2）で指定します。SettlementPayout では「underlier（対象通貨 observable）を引き渡す側が payer、受け取る側が receiver」となります（対価通貨の支払方向はその逆になります：Create_AssetFlowFromSettlementPayout product-template-func.rosetta:L94-L157）。
  • ② BuyerSeller（OptionPayout 固有）：
    オプションの権利の買い手（buyer）と売り手（seller）を Party1 / Party2 で指定します（product-template-type.rosetta:L127）。
  • ③ PartyReferencePayerReceiver（Product 外の TransferHistory 等）：
    オプション・プレミアムや決済キャッシュフローの実績（TradeState -> transferHistory）は商品テンプレートではなく具体的な当事者間の送金であるため、Party1 ではなく payerPartyReference / receiverPartyReference（@ref:external で直接 Party を指す）を使います！
common-domain-model/rosetta-source/src/main/rosetta/base-staticdata-party-type.rosetta (L18-L46)

        [metadata reference]

        [metadata reference]

4. 一次ソース検証で見つかる docs/ とスキーマの重要注意点

TradableProduct や Trade、PriceQuantity 周辺の二次資料（common-domain-model/docs/product-model.md）を一次ソースと突合すると、実務設計で致命傷になりかねない「存在しない属性（Phantom Attributes）の記述」が見つかります。

⚠️ ※ドキュメントとの差分・注意点①：PriceQuantity に settlementTerms や buyerSeller は存在しない

二次資料 common-domain-model/docs/product-model.md（L808-L816、L1063-L1065）には、「FXスポットやフォワード、オプションプレミアムでは、PriceQuantity オブジェクトの中に settlementTerms と buyerSeller 属性が含まれる」と明記されています（また product-template-type.rosetta:L319 のコメント文字列にも古い説明文が残っています）。
しかし、一次ソース observable-asset-type.rosetta:L97-L106 の PriceQuantity 型には、price, quantity, observable, effectiveDate の4属性しか存在しません。現行のCDMでは以下の場所に配置されます：

  • 決済条件（settlementTerms）と支払・受取方向（payerReceiver）→ PayoutBase（SettlementPayout や OptionPayout の親型：product-common-settlement-type.rosetta:L68-L71）
  • 買手・売手（buyerSeller）→ OptionPayout 直下（product-template-type.rosetta:L127）
  • オプション・プレミアムの受渡 → TradeState -> transferHistory（fx-ex09-euro-opt.json:L184-L221）
⚠️ ※ドキュメントとの差分・注意点②：Trade の condition SettlementPayout と FpML 変換出力のギャップ

一次ソース event-common-type.rosetta:L310-L315 の Trade 型には、condition SettlementPayout として 「SettlementPayout のみを使用する場合、Trade -> partyRole に Buyer と Seller の両方が含まれなければならない」 という制約が定義されています。
一方で、FpML Confirmation から自動変換された公式サンプル（fx-ex03-fx-fwd.json 等）では、SettlementPayout -> payerReceiver は出力されるものの、Trade -> partyRole は空のまま出力されています。したがって、システムで Trade のフルバリデーション（condition 検証）を有効化する場合は、Trade -> partyRole にも Buyer / Seller をマッピングしておく必要がある点に注意してください。

5. 実践演習①：当事者参照の追跡とCDMパスマッピング

上記セクション2〜3の一次ソース定義と公式サンプルJSON（execution-fx-forward-func-output.json / fx-ex09-euro-opt.json）に基づき、正しいマッピング先・解釈を選択して「検証」を押してください。

問1. セクション2の公式サンプルJSONにおいて、underlier である 10,000,000 EUR を実際に支払う（payer: "Party1" に該当する）金融機関のLEI はどちらか？
