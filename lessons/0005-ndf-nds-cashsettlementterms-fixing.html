NDF / NDS（SettlementPayout + cashSettlementTerms、参照通貨のFixing観測と決済通貨での差金決済）

Lesson 0004 で学んだ物理受渡（Deliverable）の FX Forward / FX Swap に続き、今回は資本規制のある新興国通貨（INR・BRL・KRW・TWD・CNY 等）で広く取引される非受渡（Non-Deliverable）型の先渡取引（NDF）および為替スワップ（NDS）を紐解きます。CDMでは新しい Payout 型を作るのではなく、同じ SettlementPayout の settlementTerms に cashSettlementTerms を付加するだけで NDF / NDS を表現します。

🎯 このレッスンの到達ゴール（Missionへの接続）

NDF（Non-Deliverable Forward）および NDS（Non-Deliverable Swap）について、参照通貨（Reference Currency）のフィキシング観測条件（ValuationMethod -> ValuationSource：FxSpotRateSource / SettlementRateOption および ValuationDate -> FxFixingDate）と決済通貨（settlementCurrency）での差金決済条件（CashSettlementTerms）、tradeLot -> priceQuantity における2通貨名目元本の保持（基準通貨 perUnitOf が常に quantity に配置される不変原則と、決済通貨／参照通貨の当てはまり方）、PayerReceiver（支払・受取）と BuyerSeller（買手・売手）の厳密な区分、さらにフィキシング確定（Reset）から差金決済（Transfer）までの状態遷移を一次ソースに基づいて設計・検証できるようになります。

1. 金融実務の NDF / NDS の仕組みと物理受渡（Forward / Swap）との CDM 構造比較

まず、為替実務における NDF・NDS の基本用語とキャッシュフローの仕組みを押さえた上で、CDM（.rosetta 一次ソース）上で物理受渡の FX Forward / FX Swap とどこが同じでどこが異なるのかを比較しましょう。

  • NDF（ノン・デリバラブル・フォワード / Non-Deliverable Forward / 非受渡先渡為替取引）：
    資本移動規制等によりオフショア（国外）での元本受渡が制限されている通貨（例：インドルピー INR、ブラジルレアル BRL、韓国ウォン KRW、台湾ドル TWD など）を対象とする先渡為替取引です。満期時に2通貨の元本を実際に交換する代わりに、「約定フォワードレート（Forward Rate）」と「決済日直前のフィキシング日に観測された公定スポットレート（Fixing Rate / Settlement Rate）」との差額（損益）だけを、自由交換可能な単一の決済通貨（主に米ドル USD）で差金決済（Net Cash Settlement）します。
  • 参照通貨（Reference Currency / Notional Currency）と決済通貨（Settlement Currency）：
    • 参照通貨（Reference Currency）：受渡が行われない規制通貨（例：INR や BRL）。計算上の名目元本（Notional Amount）および為替変動の参照対象としてのみ使われ、参照通貨建ての資金移動（Account Transfer）は一切発生しません（product-qualification-func.rosetta:L1668）。
    • 決済通貨（Settlement Currency）：差金決済の支払・受取に実際に用いられる通貨（例：USD）。SettlementTerms -> settlementCurrency に指定されます。
  • フィキシング日（Fixing Date / Valuation Date）と決済レート情報源（Valuation Source）：
    決済日（valueDate / settlementDate：通常はフィキシング日の2営業日後 T+2）に支払う差金金額を確定させるため、あらかじめ合意したフィキシング日（FxFixingDate）の特定時刻に、中央銀行や業界団体（EMTA等）が公表する公定指標レート（FxSpotRateSource の画面ページや、ISDA定義の SettlementRateOptionEnum：例 BRL.PTAX/BRL09, INR.RBIB/INR01）を観測します。
  • NDS（ノン・デリバラブル・スワップ / Non-Deliverable Swap / 非受渡為替スワップ）：
    FX Swap（期近 Near Leg と期先 Far Leg の2回の交換）の非受渡版です。Near Leg と Far Leg のそれぞれについてフィキシング日にレートを観測し、両レッグとも元本交換を行わず決済通貨（USD等）のみで差金決済を行います。

SettlementTerms -> cashSettlementTerms の4階層チェックポイント

  1. 第1層：SettlementTerms（extends SettlementBase：product-common-settlement-type.rosetta:L287-L303, L365-L389）
    condition CashSettlementTerms: if cashSettlementTerms exists then settlementType <> SettlementTypeEnum -> Physical により、cashSettlementTerms を設定するときは settlementType を Cash（またはオプション等の Election / CashOrPhysical）にする必要があります。あわせて settlementCurrency に決済通貨（例："USD"）、settlementDate -> valueDate に差金受渡日（例："2002-04-11"）を設定します。
  2. 第2層：CashSettlementTerms（product-common-settlement-type.rosetta:L108-L151）
    フィキシングの観測ソースを表す valuationMethod ValuationMethod (0..1)、フィキシング日を表す valuationDate ValuationDate (0..1)、フィキシング時刻を表す valuationTime BusinessCenterTime (0..1)（例：14:30:00 INMU［インド・ムンバイ時間］）などを束ねます。
  3. 第3層：ValuationMethod -> ValuationSource（observable-asset-type.rosetta:L437-L457）
    ValuationSource には condition InformationSource: required choice informationSource, settlementRateOption, referenceBanks, dealerOrCCP という必須4択（required choice）制約があります。為替のNDF/NDOでは以下の2パターンのいずれかを使用します：
    • パターンA（画面ページ指定：informationSource）：quotedCurrencyPair と informationSource（FxSpotRateSource -> primarySource: InformationSource、例：sourceProvider: "Reuters", sourcePage: "RBIB"）を指定（fx-ex07 の方式）。
    • パターンB（ISDA/EMTA標準コード指定：settlementRateOption）：1998 ISDA FX and Currency Option Definitions Annex A で標準化された SettlementRateOptionEnum（observable-asset-enum.rosetta:L170-L299：例 BRL_PTAX_BRL09［表示名 "BRL.PTAX/BRL09"］、CNY_SAEC_CNY01［表示名 "CNY.SAEC/CNY01"］、INR_RBIB_INR01 等）と、価格ソース混乱時のフォールバック規定 priceSourceDisruption -> fallbackReferencePrice（ValuationPostponement / fallBackSettlementRateOption / calculationAgentDetermination）を指定する方式。
  4. 第4層：ValuationDate -> FxFixingDate（product-common-settlement-type.rosetta:L97-L107, L270-L286）
    ValuationDate は5属性の one-of 制約を持ち、為替フィキシングでは fxFixingDate FxFixingDate (0..1)（または複数日スケジュールの fxFixingSchedule AdjustableDates (0..1)）を選択します。FxFixingDate は確定日付（fxFixingDate -> adjustableDate -> adjustedDate）または支払日等からの営業日オフセット（extends Offset）でフィキシング日を指定します。

3. tradeLot -> priceQuantity の解説：2通貨名目元本の保持・クオート基準・Fixingと差金決済のライフサイクル

実務システムからCDMへNDF/NDSをマッピングする際、最も質問が多いのが 「NDFは参照通貨を受け渡さないのに、tradeLot -> priceQuantity には何を入れるのか？」「フィキシング日にレートが決まったら priceQuantity を書き換えるのか？」 という点です。一次ソースから3つの鉄則を確認しましょう。

3-1. NDF でも不変の「基準通貨（perUnitOf）＝ quantity」原則と、決済通貨／参照通貨の当てはまり方

NDFをFpMLからCDMへ変換する一次ソース関数 MapFxSingleLegPriceQuantityList（ingest-fpml-confirmation-product-fxsingleleg-func.rosetta:L132-L144）は、物理受渡の FX Forward と同一の関数 MapFxCoreDetailsModelPriceQuantity（ingest-fpml-confirmation-pricequantity-func.rosetta:L1292-L1427）を呼び出します。

したがって、NDFであっても tradeLot -> priceQuantity の配置ルール自体は物理受渡と一切変わらず（何も入れ替わらず）、クオート基準がどちらであっても常に以下の不変ルールに従います：

  • 不変ルール①：為替レートの分母通貨（基準通貨：perUnitOf）の金額 ＝ 常に priceQuantity -> quantity（および observable / underlier）に配置される
  • 不変ルール②：為替レートの分子通貨（対価通貨：unit）の金額 ＝ 常に price -> derivedQuantity に配置される

では、実務のNDFデータマッピングで何に気をつける必要があるのでしょうか？
NDFには「決済通貨（settlementCurrency：実際に差金決済で授受される通貨、例 USD）」と「参照通貨（Reference Currency：受渡されない規制通貨、例 INR や BRL）」という役割区分があるため、「NDFでは quantity（あるいは underlier）に常に決済通貨（USD）を入れる決まりなのか、それとも常に参照通貨（INR / BRL）を入れる決まりなのか？」と疑問を持たれることがよくあります。
一次ソースの答えは、「決済通貨か参照通貨か」を基準に配置先を決めるのではなく、あくまで上記不変ルールどおり「為替レートの分母（基準通貨 perUnitOf）が常に quantity に配置される」ということです。その結果として、通貨ペアのクオート慣行で「決済通貨と参照通貨のどちらが基準通貨（分母 perUnitOf）に選ばれているか」によって、quantity に来るのが決済通貨になるか参照通貨になるかが決まります（fx-ex07 と fx-ex28 の比較）。

🔍 重要整理：CDM における PayerReceiver（支払い・受け取り）と BuyerSeller（買い・売り）の厳密な使い分け

為替のフロント実務では便宜上「USDの支払い」を「USDの売り」と言い換えることがありますが、CDM（.rosetta 一次ソース）では PayerReceiver（payer / receiver） と BuyerSeller（buyer / seller） を明確に別々の型として定義・分離しています（base-staticdata-party-type.rosetta:L19-L36）。payerReceiver の説明に「売り・買い」を使うと buyerSeller と混同するため、両者の役割の違いを一次ソースで押さえておきましょう。

  • ① PayerReceiver（PayoutBase -> payerReceiver：product-common-settlement-type.rosetta:L68）：
    すべてのペイアウト（SettlementPayout、InterestRatePayout、OptionPayout 等）が基底型 PayoutBase から継承する必須属性であり、「そのペイアウトの対象キャッシュフローまたは原資産（underlier＝基準通貨）を誰が支払い（payer）、誰が受け取るか（receiver）」という資金・資産移動の方向のみを表します。SettlementPayout には buyerSeller 属性は存在しません。
  • ② BuyerSeller（OptionPayout -> buyerSeller 等：product-template-type.rosetta:L127, L478, L546）：
    一次ソースの定義コメントに "The party that buys this instrument, i.e. pays for this instrument and receives the rights defined by it." と明記されているとおり、個別の通貨の支払・受取ではなく、「オプション等の金融商品（権利）を誰が買い（buyer）、誰が売ったか（seller）」を表します。
    次回 Lesson 0006 で学ぶ OptionPayout は、buyerSeller（オプションの権利自体の買手・売手）と、PayoutBase から継承した payerReceiver（権利行使された際に原資産 underlier を支払う・引き渡す側 payer と受け取る側 receiver）の「両方」を同時に持ちます（ingest-fpml-confirmation-product-fxoption-func.rosetta:L92-L107）。したがって、payerReceiver は常に「支払い（payer）・受け取り（receiver）」として一貫して扱う必要があります。
    ※なお、Product の外側にある Trade -> partyRole（event-common-type.rosetta:L305, L310-L315）には規制報告等のために取引全体の PartyRoleEnum -> Buyer / Seller を記録する制約（condition SettlementPayout）がありますが、これも PayoutBase -> payerReceiver とは別階層の属性です。
💡 実務設計の重要ポイント：対顧客NDFのマージン表現と NDS の priceQuantity

・対顧客NDFのマージン表現：Lesson 0004 と同様、PriceSchedule 直下の arithmeticOperator: "Add" は condition SpreadPrice（observable-asset-type.rosetta:L177-L179）により ExchangeRate では使えません。対顧客マージン（Sales Margin）を載せたり外したりする内訳は、PriceComposite（operandType: "Commission"）を使うか、price (0..*) 配列に「顧客約定NDFレート（price-1）」と「市場インターバンクNDFレート（Spot + ForwardPoint 内訳付き）」の2要素を並べて表現します。
・NDS（非受渡為替スワップ）の priceQuantity：単一の TradeLot 内の priceQuantity (1..*) 配列に、Near Leg 用（price-1, quantity-1, observable-1）と Far Leg 用（price-2, quantity-2, observable-2）の2要素を並べ、2つの SettlementPayout（両方とも cashSettlementTerms 付き、payerReceiver は Near と Far で支払・受取が反転）から @ref:scoped で参照します。

3-2. NDF の差金決済額（Net Cash Settlement Amount）の計算式と支払方向の決定

fx-ex07-non-deliverable-forward.json の取引条件を使って、フィキシング日（2002-04-09）に観測されたスポットレート $S_{\text{fix}}$（INR per USD）から、決済日（2002-04-11）にどちらがいくらの USD を支払うかがどう決まるかを確認しましょう。

  • 約定時の計算上の支払・受取義務の整理（fx-ex07）：
    ・基準通貨（perUnitOf = USD）名目元本 $N_{\text{USD}} = 10,000,000\text{ USD}$（quantity-1）
    ・約定フォワードレート $F = 43.40\text{ INR/USD}$（price-1 -> value）
    ・対価通貨（unit = INR）名目元本 $N_{\text{INR}} = N_{\text{USD}} \times F = 434,000,000\text{ INR}$（price-1 -> derivedQuantity）
    ・方向（payerReceiver）：underlier は基準通貨 Cash: USD であり、payer = Party1, receiver = Party2 です。つまり、満期における計算上のグロス支払・受取義務は：
    • Party1（基準通貨 USD の payer）：計算上 10,000,000 USD を支払う義務を負い、対価通貨 434,000,000 INR（＝フィキシングレート $S_{\text{fix}}$ で米ドル換算すると $\dfrac{434,000,000}{S_{\text{fix}}}\text{ USD}$）を受け取る権利を持つ立場。
    • Party2（基準通貨 USD の receiver）：計算上 10,000,000 USD を受け取る権利を持ち、対価通貨 434,000,000 INR（＝米ドル換算で $\dfrac{434,000,000}{S_{\text{fix}}}\text{ USD}$）を支払う義務を負う立場。
  • ケースA：フィキシングレートが $S_{\text{fix}} = 44.00\text{ INR/USD}$（ドル高・ルピー安）になった場合
    参照通貨 434,000,000 INR のフィキシング時点での米ドル換算価値は： $$\frac{N_{\text{INR}}}{S_{\text{fix}}} = \frac{434,000,000}{44.00} = 9,863,636.36\text{ USD}$$ Party1 は計算上 10,000,000 USD を支払って 9,863,636.36 USD 相当のルピーを受け取る立場なので、ネット差額： $$10,000,000 - 9,863,636.36 = \mathbf{136,363.64\text{ USD}}$$ を Party1（payer）から Party2（receiver）へ支払います。
  • ケースB：フィキシングレートが $S_{\text{fix}} = 42.50\text{ INR/USD}$（ドル安・ルピー高）になった場合
    参照通貨 434,000,000 INR の米ドル換算価値は $\dfrac{434,000,000}{42.50} = 10,211,764.71\text{ USD}$ となり、約定額 10,000,000 USD を上回ります。したがって、ネット差額 $\mathbf{211,764.71\text{ USD}}$ を Party2（payer）から Party1（receiver）へ支払います。

実務上、NDFのフィキシング日（例：2002-04-09）に公定レート（44.00 INR/USD）が観測された瞬間、2営業日後の受渡日（2002-04-11）に決済すべき米ドルの差金金額（136,363.64 USD）も同時に確定します。この「確定した差金金額」の格納場所について、一次ソースの3つのルールを押さえておきましょう。

  1. Reset 型（resetHistory）の中には「レート」だけが入り、「差金金額」の項目はない：
    Reset 型（event-common-type.rosetta:L223-L234）が持つのは resetValue Price (1..1)（確定レート 44.00 INR/USD）・resetDate・observations だけであり、キャッシュフロー金額（Money / Quantity）を格納する属性はありません。
  2. ⚠️ Product -> ... -> cashSettlementTerms -> cashSettlementAmount を書き換えてはいけない。：
    CashSettlementTerms には cashSettlementAmount Money (0..1) 属性（product-common-settlement-type.rosetta:L115）がありますが、これは契約締結（約定）時点であらかじめ固定決済額が合意されている特殊な契約条件用の項目です。もしフィキシング日にここを上書きすると Trade -> product（契約条件）を変更したことになり、Qualify_Reset の必須条件 beforeTradeState -> trade = afterTradeState -> trade（event-qualification-func.rosetta:L670：リセット前後で Trade 本体は同一・不変であること）に違反してしまいます。
  3. ✅ 正解：差金金額はフィキシング日の TradeState -> transferHistory に「未決済ステータス（Pending / Instructed）＋将来受渡日（2002-04-11）」の TransferState として追記する：
    CDMの Create_TradeState（event-common-func.rosetta:L2198-L2207）は、1つの PrimitiveInstruction の中に reset（ResetInstruction）と transfer（TransferInstruction）を同時に組み合わせて実行（Composite Primitive）できるよう設計されています。しかも Qualify_Reset（event-qualification-func.rosetta:L659-L672）の判定式は： 
    businessEvent -> after count = 1
    and beforeTradeState -> trade = afterTradeState -> trade
    and beforeTradeState -> resetHistory count + 1 = afterTradeState -> resetHistory count
    となっているため、フィキシング日のイベントで resetHistory（確定レート 44.00）と一緒に transferHistory（確定差金金額 136,363.64 USD、settlementDate: "2002-04-11"、transferStatus: "Pending"［指図待ち］または "Instructed"［指図済］：event-common-enum.rosetta:L66-L72）を追記しても、問題なく Reset イベントとして成立します。
    （なお、システム設計によっては「①フィキシング日は resetHistory のみ追記し、②受渡日または決済指図時に CalculateTransfer / Create_Transfer で transferHistory を追記する」という2段階分離もCDM上は許容されていますが、フィキシング時点で確定キャッシュフロー額を保持したい場合は、フィキシング日の after -> transferHistory に transferStatus: Pending / Instructed として追記するのが正規の方法です。）

C5: NDF / NDS の tradeLot -> priceQuantity と不変の配置ルール

5. 一次ソース検証で見つかる重要注意点（FpML Ingest 関数の実装ギャップと制約条件の罠）

一次ソース（rosetta-source）のテストデータと変換関数を突き合わせると、実務でNDFデータを設計・バリデーションする際に必ず知っておくべき2つの重要な注意点が浮かび上がります。

⚠️ 注意点①：なぜ fx-ex28-non-deliverable-w-disruption.json は NDF ではなく ForeignExchange_Spot_Forward と誤判定されているのか？

rosetta-source/src/main/resources/ingest/output/.../fx-ex28-non-deliverable-w-disruption.json（L8-L16）を開くと、ファイル名が non-deliverable-w-disruption（価格ソース混乱条項付き BRL/USD NDF）であるにもかかわらず、taxonomy が "ForeignExchange_Spot_Forward" になっており、settlementTerms の中に cashSettlementTerms が存在しません。

【一次ソースからの原因解明】：
入力元の FpML fx-ex28-non-deliverable-w-disruption.xml（L66-L79）では、<nonDeliverableSettlement> の子要素として <fixing> ではなく、ISDA標準コードを指定する <rateSourceFixing>（<settlementRateOption>BRL09</settlementRateOption>）および <disruption> が使われています。
ところが、CDMのFpML変換関数 MapFxCashSettlementToSettlementTerms（ingest-fpml-confirmation-settlement-func.rosetta:L513-L580）は fpmlFxCashSettlement -> fixing しかマッピングしておらず、rateSourceFixing と disruption のマッピングが未実装となっています（加えて fx-ex07.xml にある fixingTime も L576 で valuationTime: empty とハードコードされています）。
そのため fx-ex28 では cashSettlementTerms の中身がすべて empty となってJSON出力時に消滅し、cashSettlementTerms is absent となった結果、Qualify_ForeignExchange_Spot_Forward にフォールバックしてしまったのです。

【実務マッピングでの対策】：
自社システムやFpMLから BRL09 等の settlementRateOption を持つ NDF を CDM へマッピングする際は、標準 Ingest 関数をそのまま鵜呑みにせず、上のインタラクティブ探索 C3（パターンB） のとおり cashSettlementTerms -> valuationMethod -> valuationSource -> settlementRateOption（SettlementRateOptionEnum -> BRL_PTAX_BRL09）および valuationDate -> fxFixingDate を必ず出力してください。そうすれば Qualify_ForeignExchange_NDF が正しく True と判定されます。

⚠️ 注意点②：FxFixingDate の condition DateChoice と単発 NDF でのバリデーション

一次ソース product-common-settlement-type.rosetta:L284-L285 の FxFixingDate 型には、以下の制約条件が定義されています：
condition DateChoice: required choice dateRelativeToPaymentDates, dateRelativeToCalculationPeriodDates
これはもともと FpML の金利・通貨スワップ（BRL-CDI スワップ等）において「どの支払日や計算期間を基準にフィキシング日のオフセットを計算するか」を必須選択とするルール（MapFxFixingDate：ingest-fpml-confirmation-datetime-func.rosetta:L572-L594）に由来します。
一方、単発の FX NDF（fx-ex07-non-deliverable-forward.json：L64-L74）では、paymentDates スケジュールが存在しないため fxFixingDate -> adjustableDate -> adjustedDate（"2002-04-09"）のみが出力され、dateRelativeToPaymentDates と dateRelativeToCalculationPeriodDates は両方とも空となっています。CDMの型バリデータ（Data Rule Validator）を実行した際に FxFixingDate.DateChoice の警告が出た場合は、この FpML スワップ由来制約と FX 単発 NDF のギャップが原因であることを押さえておきましょう。
