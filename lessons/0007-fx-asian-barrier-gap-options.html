1. アジアン為替オプション（Asian FX Option）と、アベレージレート vs アベレージストライクの排他制約

まず、アジアン・オプション（Asian Option / 平均値オプション）の金融実務上の意味と2つの類型を確認し、続いて CDM 一次ソース（product-template-type.rosetta および product-common-schedule-type.rosetta）での表現と排他制約を読み解きます。

1-1. アジアン・オプションの金融実務概念：アベレージ・レート（Out）vs アベレージ・ストライク（In）

バニラ・オプションは満期日（1時点）の為替スポットレート $S_T$ だけで権利行使価値が決まりますが、アジアン・オプションはあらかじめ定めた観測期間（Observation Period）における複数回の為替レート観測値 $S_{t_1}, S_{t_2}, \dots, S_{t_n}$ の平均値（Average Rate：算術平均 Arithmetic または幾何平均 Geometric、単純平均 Unweighted または加重平均 Weighted）を参照する経路依存型（Path-Dependent）オプションです。
輸出入企業の月次・四半期平均建値ヘッジなどに適しており、「平均レートを決済時の参照レート（Out）に使うか、それともストライク価格自体（In）に使うか」によって以下の2種類に分かれます。

比較項目 ① アベレージ・レート・オプション
（Average Rate Option / Asian Price / Out）		 ② アベレージ・ストライク・オプション
（Average Strike Option / Floating Strike / In）
実務での仕組み ストライク価格 $K$ は約定時に固定値として合意される。
観測期間中の市場為替レートの平均値 $\bar{S}_{\text{out}}$ を満期時の最終決済参照レート（Expiration / Settlement Price）として用い、固定ストライク $K$ と比較して差金決済（または受渡精算）を行う。 		約定時点ではストライク価格が固定されておらず、観測期間中の市場為替レートの平均値 $\bar{S}_{\text{in}}$ がそのままストライク価格（変動ストライク）になる。
満期日のスポットレート $S_T$ と、確定した平均ストライク $\bar{S}_{\text{in}}$ を比較して精算する。
ペイオフ数式
（基準通貨 1単位あたり）		 ・Call：$\max(\bar{S}_{\text{out}} - K,\; 0)$
・Put：$\max(K - \bar{S}_{\text{out}},\; 0)$ 		・Call：$\max(S_T - \bar{S}_{\text{in}},\; 0)$
・Put：$\max(\bar{S}_{\text{in}} - S_T,\; 0)$
約定時点で確定している数量・価格 固定ストライク $K$ が約定時に確定しているため、基準通貨数量（quantity）と対価通貨数量（derivedQuantity $= \text{quantity} \times K$）の両方が約定時に確定する。 ストライク $\bar{S}_{\text{in}}$ が観測期間終了まで未確定であるため、約定時点では基準通貨の名目元本（quantity）のみが確定し、対価通貨数量（derivedQuantity）は約定時点では未確定（absent）となる。

1-2. CDM 一次ソースにおける2階層の排他制約（condition）とスキーマ配置

CDM の OptionPayout（product-template-type.rosetta:L126-L144）および OptionStrike（product-template-type.rosetta:L684-L694）には、アジアン・オプションに関する属性と2階層の排他制約（condition）が定義されています。まず一次ソースの定義を確認しましょう。

product-template-type.rosetta（L126-L144, L620-L634, L661-L667, L684-L694）— アジアン関連型と排他制約

type OptionStrike: <"Defines the strike price of an option.">
    strikePrice Price (0..1)
    strikeReference FixedRateSpecification (0..1) [metadata reference]
    referenceSwapCurve ReferenceSwapCurve (0..1)
    averagingStrikeFeature AveragingStrikeFeature (0..1)

    // 【排他制約②】OptionStrike 内の4属性のうち必ず1つだけを選択（strikePrice と averagingStrikeFeature は同時設定不可）
    condition:
        one-of

上記の一次ソース定義から、設計・レビュー時に押さえるべき3つの構造ルールが導かれます：

  1. 排他制約①：OptionStrike 内の condition: one-of（L692-L693）：
    OptionStrike は strikePrice（固定ストライク価格）と averagingStrikeFeature（平均観測による変動ストライク条件）のどちらか1つしか持てません。したがって、アベレージ・レート・オプション（固定ストライク $K$ がある取引）では必ず strike -> strikePrice を使用し、strike -> averagingStrikeFeature は空（absent）になります。逆に、strike -> averagingStrikeFeature を使用するアベレージ・ストライク・オプションでは、strike -> strikePrice を同時に設定することはできません。
  2. 排他制約②：OptionPayout の AsianOptionChoice_*（L137-L144）：
    OptionPayout -> feature -> averagingFeature（AveragingFeature 型）と、OptionPayout -> strike -> averagingStrikeFeature（AveragingStrikeFeature 型）は、同一の OptionPayout 内で同時に存在することが禁止（相互排他）されています。
    なぜなら、AveragingFeature 自体が averagingInOut（In：平均ストライク、Out：平均決済価格、Both：両方平均、product-template-enum.rosetta:L6-L10）という属性を持っており、もし feature -> averagingFeature と strike -> averagingStrikeFeature の両方を許すと平均ストライク条件が2箇所に重複定義されてしまうためです。
  3. 為替のアベレージ・レート・オプション（fx-ex20〜fx-ex22）における CDM の2つの表現ルート：
    一次ソースの FpML 変換関数 MapFxOptionPayout（ingest-fpml-confirmation-product-fxoption-func.rosetta:L108-L110, L137-L192）および検証済み JSON を確認すると、CDM には平均観測条件の格納先として以下の2つの正規ルートが存在します：
    • ルートA（FX FpML Ingest 標準：OptionPayout -> observationTerms ＋ strike -> strikePrice）：
      FpML の <fxOption><features><asian> を変換した検証済み JSON（fx-ex20-avg-rate-option-parametric.json:L38-L74）で使われている構造です。固定ストライクを strike -> strikePrice に置き、為替フィキシング時刻（observationTime）・情報ソース（informationSource: FxSpotRateSource）・観測日スケジュール（observationDates）を OptionPayout -> observationTerms（product-common-schedule-type.rosetta:L174-L187）に格納します。
    • ルートB（OptionFeature -> averagingFeature または OptionStrike -> averagingStrikeFeature を用いる構造）：
      平均計算手法（averagingCalculation：算術／幾何平均 calculationMethod、加重有無 isWeighted、端数処理 precision: Rounding）や市場混乱時規定（marketDisruption）まで明示する場合は、アベレージ・レートなら OptionPayout -> feature -> averagingFeature（averagingInOut: Out）＋ strike -> strikePrice、アベレージ・ストライクなら OptionPayout -> strike -> averagingStrikeFeature（内部に averagingCalculation と observationTerms の両方を持つ）を使用します。なお、ルートAの OptionPayout -> observationTerms は AsianOptionChoice_* の排他対象外であるため、feature -> averagingFeature と併用して情報ソース（FxSpotRateSource）を補完することも可能です。
💡 深掘り解説：① なぜ平均ストライクの表現が2つあるのか？ ②「In / Out」の語源 ③「Both」と排他制約の関係
  • ① なぜ averagingFeature と averagingStrikeFeature の2系統が存在し、どう使い分けるのか？
    一次ソースの履歴（CDM 7 PR #3827 / RELEASE.md）および型構造を見ると、この2つは設計の出自と保持できる属性が異なります：
    • もともとの CDM ネイティブ設計（概念分離型）：初期の CDM では、OptionFeature 側には平均決済価格用の AveragingCalculation のみを置き（そのため現在も product-template-type.rosetta:L664 の averagingFeature の説明文には "an average market observation price is determined on valuation and compared to the strike" とアベレージ・レート前提の記述が残っています）、平均ストライクは「ストライク価格の決定方式の1つ」として OptionStrike -> averagingStrikeFeature（L631-L634, L690）に分離していました。
    • FpML Equity Asian Option（ISDA 2002 Equity Definitions）統合による拡張：一方、FpML の株式オプション（eqd-ex05-asian-long-form.xml, eqd-ex06-averaging-in-long-form.xml）では、平均ストライク（In）・平均決済価格（Out）・両方平均（Both）をすべて単一の <feature><asian> タグで表現します。これを取り込むため、AveragingFeature 型（旧 Asian 型）が OptionFeature -> averagingFeature に接続され、既存の OptionStrike -> averagingStrikeFeature と重複しないよう condition AsianOptionChoice_* で排他制御されました。
    • 構造上の使い分け（ObservationTerms vs AveragingPeriod）：AveragingStrikeFeature（L631-L634）は内部に observationTerms: ObservationTerms を持ち、為替フィキシングに必要な画面ソース（informationSource: FxSpotRateSource）や観測時刻（observationTime: BusinessCenterTime）を直接格納できます。これに対し、AveragingFeature が持つ averagingPeriodIn / averagingPeriodOut（AveragingPeriod 型、product-common-schedule-type.rosetta:L242-L252）には日時リストと marketDisruption しかなく FxSpotRateSource を持ちません。したがって、為替の純粋なアベレージ・ストライク・オプションを CDM ネイティブに表現する場合は OptionStrike -> averagingStrikeFeature が適しており、FpML <asian> 構造の取り込みや後述の Both（ダブル・アジアン）や strikeFactor を使う場合は OptionFeature -> averagingFeature（＋必要に応じ OptionPayout -> observationTerms で為替ソースを補完）を使い分けます。
  • ② なぜ平均ストライクを In、平均決済価格を Out と呼ぶのか？（金融実務での語源）
    product-template-enum.rosetta:L6-L10 の AveragingInOutEnum における In / Out は、ISDA 2002 Definitions および市場慣行の 「Averaging-In（平均イン）」「Averaging-Out（平均アウト）」 という用語に由来します：
    • In（Averaging-In ＝ 取引の「入口」の建値・ストライク価格の平均化）：オプションのストライク価格とは、ポジションに参入（Entry ＝ In）する際の基準建値に相当します。取引初期（または一定期間）の観測レートを平均して「段階的にストライク（建値）へ入っていく（average into the strike）」ことから In（averagingPeriodIn） と呼ばれます。
    • Out（Averaging-Out ＝ 取引の「出口」の満期決済価格の平均化）：満期時の決済参照価格（Expiration / Settlement Price）とは、ポジションから退出・精算（Exit ＝ Out）する際の出口価格に相当します。満期に向けた観測期間のレートを平均して「段階的に手仕舞い価格を確定させて出ていく（average out of the position）」ことから Out（averagingPeriodOut） と呼ばれます。
  • ③ AveragingInOutEnum -> Both は排他制約に違反しないのか？FX で使われることはあるか？
    • 排他制約との関係（違反せずに表現可能）：Both（入口期間の平均レートでストライク $\bar{S}_{\text{in}}$ を決め、出口期間の平均レートで満期決済レート $\bar{S}_{\text{out}}$ を決めるダブル・アジアン / Double Asian Option）を表現する場合、strike -> averagingStrikeFeature は使用せず（absent にし）、OptionPayout -> feature -> averagingFeature 1箇所の中だけで averagingInOut: Both と averagingPeriodIn（入口期間）・averagingPeriodOut（出口期間）の両方を設定します。そのため、strike -> averagingStrikeFeature は空のままであり、排他制約①（OptionStrike の one-of）にも排他制約②（AsianOptionChoice_*）にも抵触しません。
    • 為替（FX）での扱い：FpML の為替オプション標準スキーマ（<fxOption><features><asian>）は単一観測期間＋固定ストライク（Out 相当）のみを想定しているため FpML FX の標準サンプルには Both は含まれませんが、実務の相対（OTC）為替デリバティブで「第1四半期の平均レートをストライクとし、第4四半期の平均レートで精算する」といった Double Average Rate Option を組成し CDM で表現する際には、この feature -> averagingFeature（averagingInOut: Both ＋ averagingPeriodIn ＋ averagingPeriodOut）を用いて表現できます。

1-3. 一次ソース実データ検証：ObservationTerms の構造と観測日スケジュール（パラメトリック期間 vs 個別観測日・加重ウェイト）

為替のアベレージ・レート・オプションにおいて「いつ・どの画面ソースで・どの日程と重み付け（Weight）でスポットレートを観測するか」を定義するのが ObservationTerms および ObservationDates（product-common-schedule-type.rosetta:L151-L187）です。まず一次ソースの型定義を確認しましょう。

この一次ソース定義の通り、CDM の正規スキーマでは、観測条件（ObservationTerms）を以下の3つの要素で構成します：

  1. 観測時刻と情報ソース（observationTime & informationSource）：
    フィキシングを行う現地時刻と営業日カレンダー（例：メキシコシティ 18:00:00 MXMC や東京 15:00:00 JPTO）を observationTime（BusinessCenterTime 型）に設定し、参照する為替レート画面（例：Reuters の BNBX ページ）を informationSource -> primarySource（FxSpotRateSource 型）に設定します。
  2. 観測日程の表現パターン①：パラメトリック期間指定（observationDates -> periodicSchedule）：
    「2001年11月1日から2001年11月30日まで」のように開始日（startDate）・終了日（endDate）・周期（periodFrequency）で観測期間を定義する場合は、observationDates -> periodicSchedule（PeriodicDates 型）を使用します。各観測日の重み（weight）を個別に指定しない場合、すべての観測日の重みは等しく 1.0 として扱われます。

2. バリア為替オプション（FX Barrier Option）：Knock-in / Knock-out / Double Barrier / Rebate

次に、為替オプション市場で最も取引量の多いエキゾチック商品であるバリア・オプション（FX Barrier Option）の実務概念と、CDM の OptionPayout -> feature -> barrier（Barrier 型）および TriggerEvent / Trigger / FeaturePayment の階層構造を確認します。

2-1. バリア・オプションの金融実務概念と基本類型

バリア・オプション（Barrier Option）とは、観測期間中に原資産の為替スポットレートがあらかじめ定めたバリア水準（トリガーレート / Barrier Level / Trigger Rate）に到達（Breach / Touch）したかどうかに応じて、オプション権利が有効化（ノックイン / Knock-in）されたり、消滅（ノックアウト / Knock-out）したりする条件付きオプションです。

  • ノックイン（Knock-in：Barrier -> knockIn）：
    約定時点ではオプション権利はまだ有効ではなく（休眠状態）、観測期間中に市場レートがバリア水準に到達して初めて通常のバニラ・オプション（Call または Put）として有効化されます。現在のスポットレートより高いバリアへの上昇で有効化されるものを Up-and-In（triggerType: EqualOrGreater）、低いバリアへの下落で有効化されるものを Down-and-In（triggerType: EqualOrLess）と呼びます（例：fx-ex12-fx-barrier-option.xml は約定時スポット 0.8935 USD/EUR、ストライク 0.9000 USD/EUR、トリガー 0.8975 USD/EUR の Up-and-In EUR Call）。
  • ノックアウト（Knock-out：Barrier -> knockOut）：
    約定時点では有効なオプションとして存在しますが、観測期間中に市場レートがバリア水準に一度でも到達すると、その時点でオプション権利が消滅（Null and Void）します。高いバリアへの上昇で消滅するものを Up-and-Out、低いバリアへの下落で消滅するものを Down-and-Out と呼びます。
  • ダブル・バリア（Double Barrier）と KIKO（Knock-in Knock-out）：
    下限バリア（Lower Trigger）と上限バリア（Upper Trigger）の2つの水準を設定し、期間中にどちらかに到達したら消滅する Double Knock-out（例：fx-ex13-fx-dbl-barrier-option.xml：スポット 106 JPY/USD、ストライク 105.05 JPY/USD、下限 102 JPY/USD または上限 115 JPY/USD 到達で消滅する JPY Put / USD Call）、どちらかに到達したら有効化される Double Knock-in、さらに片方でノックイン・もう片方でノックアウトする KIKO（Knock-in Knock-out）があります。
  • 連続監視（Anytime）vs 終値・離散監視（Closing）とリベート（FeaturePayment）：
    FXバリア・オプションでは、観測期間中のどの時点でも市場レートがバリアにタッチすれば発動する連続監視（Continuous Barrier：TriggerTimeTypeEnum -> Anytime）が標準的ですが、特定の営業日終値・カットオフ時刻のみで判定する離散・終値監視（Window / Discrete Barrier：TriggerTimeTypeEnum -> Closing）もあります。また、ノックアウト等で権利が消滅した際に買手へ一定の補償金を支払う条件をリベート（Rebate：TriggerEvent -> featurePayment）と呼びます。

  1. 複数カーディナリティ (0..*) によるダブル・バリアと KIKO の表現：
    Barrier 型の knockIn と knockOut はどちらも TriggerEvent (0..*)（0個以上の配列）です。
    たとえば fx-ex13（下限 102 JPY/USD で Down-and-Out、上限 115 JPY/USD で Up-and-Out のダブル・ノックアウト）を表現する場合、knockOut 配列に2つの TriggerEvent 要素を格納します（1つ目は level.value: 102.0, triggerType: "EqualOrLess"、2つ目は level.value: 115.0, triggerType: "EqualOrGreater"）。このように2要素に分けることで、下限と上限それぞれの発動方向（triggerType）を明確に保持できます。また、KIKO バリアであれば knockIn に1要素、knockOut に1要素を同時に設定します。
  2. Trigger の必須選択制約 condition Choice1（L20-L21）：
    Trigger 型では level（価格・為替レート水準）、creditEvents、creditEventsReference の3属性に対して required choice が課されています。クレジット・デフォルト・スワップション（cd-swaption-1.json:L37-L45）では creditEventsReference を使いますが、為替バリア・オプションでは必ず level（PriceSchedule 型：value, unit, perUnitOf, priceType: "ExchangeRate"）を選択します。
  3. FeaturePayment（リベート等）における PartyReferencePayerReceiver と required choice：
    ノックアウト時のリベート支払等を表す FeaturePayment（L85-L101）では、① payerReceiver の型が抽象ロール（Party1/Party2）の PayerReceiver ではなく、Party 実体（@ref:external: "party1" 等）を参照する PartyReferencePayerReceiver である点、および ② condition FeaturePaymentChoice により levelPercentage（比率）か amount（非負の金額）のどちらか一方が必須（required choice）である点に注意してください。
  4. バリア判定代理人（BarrierDeterminationAgent）の表現：
    実務契約（Confirmation）では「バリアにタッチしたかどうかを誰が判定するか」としてバリア判定代理人（Barrier Determination Agent）を指定します。CDM では Trade -> partyRole に role: PartyRoleEnum -> BarrierDeterminationAgent（base-staticdata-party-enum.rosetta:L67）を設定し、Trade の制約 condition BarrierDerterminationAgent（event-common-type.rosetta:L406-L408）により「1件の取引に BarrierDeterminationAgent は最大1者まで（count <= 1）」と検証されます。

3. ギャップ・オプション（Gap Option）の一次ソース導出：ストライク $K_1$ vs トリガー $K_2$ の分離表現

続いて、MISSION.md のターゲット商品であるギャップ・オプション（Gap Option）について、金融実務での意味（バニラ・オプションおよびデジタル・オプションとの違い）を整理し、一次ソースの型制約（product-template-type.rosetta / observable-event-type.rosetta）から正規の CDM スキーマ構造を導出します。

3-1. バニラ vs デジタル（バイナリー）vs ギャップ・オプションの3者比較

通常のバニラ・オプションでは、「権利が行使されるかどうかの発動閾値」と「権利が行使されたときにいくらで交換・精算するかの計算基準レート」が同一のストライクレート $K$ です。
これに対し、ギャップ・オプション（Gap Option）では、① ペイオフ計算（または2通貨交換金額）の基準となるストライク価格 $K_1$（Strike Price）と、② 権利が有効化・行使されるかを決めるトリガー価格 $K_2$（Trigger Level, $K_1 \neq K_2$）が別々の値として分離しています。

3-2. ギャップ・オプションの CDM スキーマ導出（$K_1$ と $K_2$ のマッピング）

実務における為替ギャップ・オプション（例：基準通貨名目元本 10,000,000 USD、ストライク $K_1 = 150.00\text{ JPY/USD}$、満期トリガー $K_2 = 155.00\text{ JPY/USD}$ の USD/JPY Gap Call Option）は、実質的に「満期日（expirationDate）の判定時刻において $S_T \ge K_2$（155.00 JPY/USD）となった場合にのみ有効化（Knock-in）され、有効化された場合はストライク $K_1$（150.00 JPY/USD）で 10,000,000 USD と 1,500,000,000 JPY を交換（または差金決済）するヨーロピアン・ノックイン・オプション」と同じ経済構造を持ちます。

  1. ストライク価格 $K_1$（150.00 JPY per USD）の配置：
    OptionPayout -> strike -> strikePrice に $K_1$（value: 150.00, unit: JPY, perUnitOf: USD, priceType: ExchangeRate）を設定します。
  2. トリガー価格 $K_2$（155.00 JPY per USD）の配置：

② アベレージ・ストライク

③ バリア・オプション
（Barrier Option）

④ ギャップ・オプション
（Gap Option：$K_1 \neq K_2$）		 ・strike -> strikePrice：精算・交換基準のストライク $K_1$

（feature -> barrier が存在するため、プレーンバニラ判定から除外される）

ギャップ・オプション（ストライク $K_1$ vs トリガー $K_2$）の構造

金融実務での意味：満期時（または観測時）のレート $S_T$ がトリガー水準 $K_2$ を超えた（Call の場合 $S_T \ge K_2$）ときに限り発動し、発動時の交換・精算レートには $K_2$ ではなくストライク価格 $K_1$（$K_1 \neq K_2$）を用いるオプションです。

CDM での役割：精算・交換基準となるストライク $K_1$ を OptionPayout -> strike -> strikePrice に配置し、発動閾値となるトリガー $K_2$ を OptionPayout -> feature -> barrier -> knockIn[0] -> trigger -> level[0] に配置することで、2つのレート水準の役割を曖昧さなく分離して表現します。
