Phase 3 · Lesson 0006 · Foreign Exchange Derivatives (FX Vanilla Option & Non-Deliverable Option)

為替オプション① 基本構造（FX Vanilla Option / NDO：OptionPayout, BuyerSeller, OptionTypeEnum, ExerciseTerms, OptionStrike）

Lesson 0004〜0005 では、確定した受渡・差金決済義務を表す SettlementPayout を学びました。今回からは、権利の買手（buyer）が行使（Exercise）を選択できる為替オプション（FX Option）に入り、その中核となる OptionPayout の構造を紐解きます。特に「為替のコール／プット（通貨Aのコール＝通貨Bのプット）をCDMはどう正規化するのか？」「buyerSeller と payerReceiver はどう違うのか？」「ストライク価格とオプション料（プレミアム）は PriceQuantity のどこに入るのか？」を一次ソースから解明します。

🎯 このレッスンの到達ゴール（Missionへの接続）

バニラ為替オプション（FX Vanilla Option：ヨーロピアン／アメリカン）および非受渡為替オプション（NDO：Non-Deliverable Option）について、① OptionPayout が持つ buyerSeller（オプション権利の買手・売手）と payerReceiver（原資産 underlier の支払・受取方向）の厳密な区分と権利行使時の Put 反転ロジック（Create_Exercise）、② クオート基準（分母通貨 perUnitOf）に基づく optionType（Call / Put）と2通貨数量（quantity vs derivedQuantity）の決定ルール、③ ExerciseTerms・OptionStrike・SettlementTerms（NDOの cashSettlementTerms）、および ④ オプション・プレミアムの表現（transferHistory vs priceQuantity）を一次ソースに基づいて設計・レビューできるようになります。

1. 為替オプションの基本概念と、CDMにおける2つの設計ポイント

まず、為替オプションの金融実務用語と、それをCDM（.rosetta 一次ソース）へマッピングする際の2つのルールを押さえましょう。

  • 為替オプション（FX Vanilla Option / Foreign Exchange Option）：
    将来の特定の期日または期間内に、あらかじめ合意した為替レート（ストライク価格 / 行使価格 / Strike Price）で、一定の2通貨の金額（コール通貨額 Call Currency Amount と プット通貨額 Put Currency Amount）を交換する「権利（義務ではない）」を売買する取引です。権利の買手（buyer）は売手（seller）に対してオプション料（プレミアム / Option Premium）を支払います。
  • NDO（ノン・デリバラブル・オプション / Non-Deliverable Option / 非受渡為替オプション）：
    Lesson 0005 で学んだ NDF のオプション版です。資本規制のある参照通貨（例：BRL、INR、KRW、VEB等）を対象とし、満期日にイン・ザ・マネー（In-the-Money）となって権利行使された場合、2通貨の元本交換は行わず、フィキシング日に観測されたスポットレートとストライク価格の差額（本質的価値 / Intrinsic Value）のみを決済通貨（主に USD）で差金決済します。

設計ポイント①：BuyerSeller（権利の買手・売手）と PayerReceiver（原資産の支払・受取）の同時保持

Lesson 0005 の質疑応答でも確認したとおり、CDMには当事者の方向を表す型として BuyerSeller と PayerReceiver が明確に区別されて存在します（base-staticdata-party-type.rosetta:L18-L35）。
OptionPayout（product-template-type.rosetta:L126-L136）は PayoutBase を継承（extends PayoutBase）しているため、buyerSeller (1..1) と payerReceiver (1..1) の両方を必須属性として同時に保持します。

  • OptionPayout -> buyerSeller（BuyerSeller 型）：
    オプション契約（権利という金融商品）の「買手（buyer）」と「売手（seller）」を表します。権利行使を選択できるのは buyer であり、プレミアムを支払うのも原則として buyer です。
  • OptionPayout -> payerReceiver（PayoutBase から継承された PayerReceiver 型）：
    権利行使された場合に生じる原資産（underlier）の計算上の「支払者（payer）」と「受取者（receiver）」を表します。
    一次ソースの FpML 変換関数 MapFxOptionPayout（ingest-fpml-confirmation-product-fxoption-func.rosetta:L92-L107）および MapSellerAsPayerAndBuyerAsReceiver（ingest-fpml-confirmation-party-func.rosetta:L844-L862）では、オプション約定時の初期値として常に「オプションの売手（seller）＝ payer、オプションの買手（buyer）＝ receiver」（すなわち Call オプションで buyer が原資産 underlier を受け取る方向）に正規化してセットされます。
  • では、Put オプション（買手が原資産 underlier を支払う権利）のときはどうなるのか？：
    ここが一次ソースを読まないと気づけないポイントです。Put オプションであっても、OptionPayout 上の payerReceiver は payer: seller, receiver: buyer のまま保持されます（fx-ex09-euro-opt.json:L28-L31, L42-L45, L50）。その代わり、権利行使イベントを実行する一次ソース関数 Create_Exercise（event-common-func.rosetta:L520-L527）において、if optionPayout -> optionType = Put then Update_ProductDirection(...) が呼ばれ、行使によって生成される決済取引（FX Spot/Forward）の payer と receiver が自動的に反転（Flip）される設計になっています。

設計ポイント②：「通貨Aのコール＝通貨Bのプット」をどう一意に Call または Put に決めるのか？

為替オプションでは、たとえば「買手（Party1）が 1 AUD = 0.4920 USD のストライクで 75,000,000 AUD を支払い（Put）、36,900,000 USD を受け取る（Call）権利」は、見方によって「AUD プット」とも「USD コール」とも呼べます。実務の FpML でも putCurrencyAmount (75,000,000 AUD) と callCurrencyAmount (36,900,000 USD) の両方を並列に記述します。
しかし CDM の OptionPayout -> optionType には Call か Put のどちらか1つしか入りません。どちらになるかは、Lesson 0003〜0005 で貫いてきた「為替レートの分母通貨（基準通貨 perUnitOf）が常に quantity および underlier になる」という不変原則から機械的に決まります（ingest-fpml-confirmation-product-fxoption-func.rosetta:L119-L122, L194-L249, L251-L314）：

  1. ステップ1（基準通貨 perUnitOf ＝ underlier & quantity の特定）：
    ストライクレートのクオート基準（strikeQuoteBasis）を見ます。分母通貨（perUnitOf：「1単位あたり」の基準通貨）が常にこのオプションの原資産（underlier ＝ Cash）および priceQuantity -> quantity となり、分子通貨（unit：対価通貨）が price -> derivedQuantity となります。
  2. ステップ2（基準通貨 underlier に対する権利が Call か Put かの決定）：
    オプションの買手（buyer）にとって、その基準通貨（perUnitOf ＝ underlier）を受け取る権利であれば optionType: "Call"、基準通貨（perUnitOf ＝ underlier）を支払う権利であれば optionType: "Put" となります（ingest-fpml-confirmation-other-func.rosetta:L2300-L2305 の MapPutCallEnum）。

アメリカン・バニラ（fx-ex10）と 非受渡 NDO（fx-ex11）ではどこが変わるのか？

  • アメリカン・オプション（fx-ex10-amer-opt.json:L51-L75）の差分：
    exerciseTerms -> style が "American" になり、権利行使可能期間の開始日を表す commencementDate（例：unadjustedDate: "2001-12-04"）が追加されます。一次ソースの ExerciseTerms（product-template-type.rosetta:L744-L758）には以下の排他制約（condition）が定義されています：
    • condition AmericanExercise：style = American のとき、commencementDate exists（必須）かつ expirationDate count = 1。
    • condition EuropeanExercise：style = European のとき、expirationDate exists かつ commencementDate is absent（設定禁止）、multipleExercise is absent、latestExerciseTime is absent。
  • NDO（非受渡オプション：fx-ex11-non-deliverable-option.json:L36-L86）の差分：
    Lesson 0005 で学んだ「FX Forward に cashSettlementTerms を付けると NDF になる」のと同じ compositional（部品合成）設計です。
    すなわち、OptionPayout -> settlementTerms に settlementType: "Cash"、settlementCurrency: "USD"、そしてフィキシング観測条件を定義した cashSettlementTerms（valuationMethod -> valuationSource、valuationDate -> fxFixingDate、valuationTime）を追加するだけで NDO になります。

3. OptionStrike vs tradeLot -> priceQuantity vs Premium の解説

FX Forward / NDF と FX Option を比較したとき、実務マッピング担当者が疑問に思うのが 「為替オプションには①ストライクレート、②2通貨の名目元本、③約定時スポットレート、④オプション・プレミアム（金額および相場％／pips）があるが、それぞれ OptionPayout と tradeLot -> priceQuantity と transferHistory のどこに入れるのか？」 という点です。一次ソースの変換関数と制約（condition）から4つの核心を整理しましょう。

3-1. なぜストライクレートは tradeLot -> priceQuantity -> price.value ではなく OptionPayout -> strike -> strikePrice に入るのか？

FX Forward では約定フォワードレートを tradeLot -> priceQuantity -> price[0] -> value に入れていました。一方、FX Option（fx-ex09 / fx-ex10 / fx-ex11）では、ストライクレート（0.4920 USD/AUD や 1.15 VEB/USD）は OptionPayout -> strike -> strikePrice（Price 型）に格納され、tradeLot -> priceQuantity -> price[0] には value を入れず derivedQuantity（対価通貨の名目元本）のみが格納されています（ingest-fpml-confirmation-product-fxoption-func.rosetta:L205-L314）。

なぜかというと、オプションにおいて「ストライク価格（行使価格 K）」は、将来イン・ザ・マネーかアウト・オブ・ザ・マネーかを判定する商品契約のペイアウト計算パラメータ（Product -> EconomicTerms の一部）である一方、「そのオプション取引をいくらで売買したか」という取引約定価格（Trade Price）は本来「オプション・プレミアム（Option Premium）」だからです。

  • 約定時スポットレート（Spot Rate）が FpML にある場合：
    MapFxOptionStrikePrice（ingest-fpml-confirmation-product-fxoption-func.rosetta:L231-L249）の通り、OptionPayout -> strike -> strikePrice -> composite -> baseValue に約定時のスポットレート（fpmlFxOption -> spotRate）が格納されます。
  • tradeLot -> priceQuantity -> price[0] で value が空でもエラーにならない理由：
    PriceSchedule（observable-asset-type.rosetta:L135-L203）は MeasureSchedule（value (0..1) が任意）を継承しており、value を空にして derivedQuantity（36,900,000 USD）だけを保持することが許されています。さらに Lesson 0003 で学んだ三角整合性ルール PriceQuantityTriangulation（observable-common-func.rosetta:L18-L38）および CashPriceQuantityNoOfUnitsTriangulation（L58-L78）は、price -> priceType = CashPrice 等が存在する場合にのみチェックを行うため、priceType と value を空にした derivedQuantity ホルダーはバリデーションを正常に通過します。

3-2. オプション・プレミアム（Option Premium）の2つの表現場所と二次資料（docs/）とのギャップ注意点

では、買手から売手へ支払われるオプション・プレミアム（例：fx-ex09 の 36,900 USD、決済日 2001-12-06）はどこにマッピングされるのでしょうか？

⚠️ 二次資料（docs/product-model.md）との差分・注意点（一次ソースによる裏付け）

二次資料の common-domain-model/docs/product-model.md（L847-L851）には、「An option trade will contain an instance of a PriceQuantity containing only the premium as price attribute, but no quantity or observable」と記載されています。
しかし、一次ソースの FpML 変換関数および検証済みJSON（fx-ex09, fx-ex10, fx-ex11, fx-ex20 等すべて）を検証すると、FpMLの <premium> は tradeLot -> priceQuantity ではなく、TradeState -> transferHistory 内の UnscheduledTransfer（transferType: "Premium"）にマッピングされています（ingest-fpml-confirmation-payment-func.rosetta:L106-L107, L412-L421）。

さらに、MapFxOptionPremiumListToTransferStateList（L421）の末尾には // TODO map other fields というコメントが残されており、FpMLの <fxOptionPremium> に含まれる <quote>（プレミアム相場：例 0.001 USD per AUD や額面比％）や <settlementInformation> は現行のFpMLインジェスト関数ではまだマッピングされていません。
実務システムで「プレミアムのキャッシュフロー金額（例：36,900 USD）」と「プレミアムの単価・料率（例：0.000492 USD per AUD）」の両方をCDMで保持したい場合は、以下の2箇所を併用するのが一次ソースの型定義に適合する正規の設計です：

  1. プレミアムの決済キャッシュフロー（誰から誰へ・いつ・いくら支払うか）：
    TradeState -> transferHistory に UnscheduledTransfer（transferType: UnscheduledTransferEnum -> Premium、quantity: 36,900 USD、settlementDate: 2001-12-06、payerReceiver: party1 -> party2）として記録する（fx-ex09-euro-opt.json:L184-L221）。
  2. プレミアムの約定単価・料率（1単位あたりいくらのプレミアムで取引したか）や一部解約時のフィー：
    tradeLot -> priceQuantity の price に priceType: PriceTypeEnum -> CashPrice（および必要に応じて datedValue や composite）として保持する（observable-asset-enum.rosetta:L376-L380, event-common-type.rosetta:L166）。

3-3. 為替オプションのライフサイクル（権利行使・一部行使・消滅）における priceQuantity の変化

約定した為替オプションが満期または期中に迎えるライフサイクルイベントにおいて、TradeState と tradeLot -> priceQuantity がどう変化するかを一次ソース関数 Create_Exercise（event-common-func.rosetta:L498-L553）で確認しましょう。

  1. 全額権利行使（Full Exercise）：
    Create_Exercise は2つの TradeState を出力します：
    • ① 元のオプション取引（originalTrade）：exerciseInstruction -> exerciseQuantity（減額指示 QuantityChangeDirectionEnum -> Decrease 等）によって tradeLot -> priceQuantity の quantity（および derivedQuantity）が 0 に減額され、state -> positionState = Closed となって終了します。
    • ② 行使によって新たに成立する直物／先渡取引（Replacement Trade）：物理受渡オプションの場合、原資産（Cash: AUD）の SettlementPayout を持つ新しい TradeState が生成されます。この際、元のオプションの tradeLot -> priceQuantity（75,000,000 AUD と 36,900,000 USD）がそのまま新しい決済取引の priceQuantity として引き継がれ（L533）、optionType = Put であれば Update_ProductDirection（L520-L527）によって SettlementPayout -> payerReceiver が payer: Party1 (Buyer), receiver: Party2 (Seller) に反転されます。
  2. 一部権利行使（Partial Exercise）または一部解約（Partial Termination）：
    ExerciseTerms -> partialExercise（またはアメリカンの multipleExercise）に基づき、たとえば名目元本 75,000,000 AUD のうち 25,000,000 AUD だけを行使（または一部解約）した場合、元のオプションの tradeLot -> priceQuantity は残存元本（quantity: 50,000,000 AUD、derivedQuantity: 24,600,000 USD）に更新され、行使された 25,000,000 AUD 分についてのみ決済（または 新規 SettlementPayout 取引／差金 Transfer）が生成されます。
  3. アウト・オブ・ザ・マネーでの権利放棄・失効（Expiry / Abandonment）：
    満期日（expirationDate）のカットオフ時刻（expirationTime）にアウト・オブ・ザ・マネーであった場合、決済取引や決済キャッシュフローは一切生成されず、オプション取引の quantity が 0（Closed）となって消滅します。

4. 製品分類の自動判定：Qualify_ForeignExchange_VanillaOption vs Qualify_ForeignExchange_NDO

CDM が EconomicTerms の構造からどの為替オプション商品かを自動判定する2つの一次ソース関数（product-qualification-func.rosetta:L1754-L1785）を1行ずつ確認しましょう。

product-qualification-func.rosetta（L1754-L1785）— バニラ為替オプションと NDO の判定ロジック 
// 1. 物理受渡の為替バニラオプション（およびアベレージレート・オプション）の判定
func Qualify_ForeignExchange_VanillaOption:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style <> OptionExerciseStyleEnum -> Bermuda)
            and (optionPayout -> feature is absent
                or optionPayout -> feature -> averagingFeature only exists)
            and optionPayout -> settlementTerms -> cashSettlementTerms is absent

// 2. 非受渡為替オプション（NDO: Non-Deliverable Option）の判定
func Qualify_ForeignExchange_NDO:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style = OptionExerciseStyleEnum -> European)
            and optionPayout -> settlementTerms -> cashSettlementTerms exists
💡 一次ソースの Qualification 関数から読み取れる3つの重要事実
  1. バニラオプションと NDO の分岐点も cashSettlementTerms の有無：
    Lesson 0005 の「FX Forward vs NDF」とまったく同じように、単一の OptionPayout において settlementTerms -> cashSettlementTerms is absent なら ForeignExchange_VanillaOption、cashSettlementTerms exists（かつ style = European）なら ForeignExchange_NDO と判定されます。
  2. Qualify_ForeignExchange_VanillaOption の行 L1766-L1768 の特徴：
    ① style <> Bermuda（ヨーロピアンまたはアメリカンのみ）、② feature is absent or feature -> averagingFeature only exists（feature が空であるか、または次回の Lesson 0007 で学ぶアベレージレート条件 averagingFeature のみを持つ場合も ISDA Taxonomy 上 ForeignExchange_VanillaOption に含まれる）という条件になっています。
  3. NDO は European スタイル専用：
    Qualify_ForeignExchange_NDO（L1783）には optionPayout -> exerciseTerms -> style = OptionExerciseStyleEnum -> European が課されています。これは実務上、NDO が満期日の公定フィキシングレート（FxFixingDate）との差額で差金決済されるヨーロピアン型として取引されることに対応しています。

buyerSeller vs payerReceiver と Put 行使時の方向反転

金融実務とCDMの厳密な区分：
・buyerSeller：オプションという「権利」を買った当事者（buyer）と売った当事者（seller）。
・payerReceiver：原資産（underlier ＝ 基準通貨）を「支払う当事者（payer）」と「受け取る当事者（receiver）」。

なぜ Put でも約定時の payerReceiver は payer: Seller, receiver: Buyer なのか？：
MapFxOptionPayout は MapSellerAsPayerAndBuyerAsReceiver を使って、常にオプションの売手を payer、買手を receiver にセットします。そして権利行使関数 Create_Exercise が実行される際、if optionPayout -> optionType = Put then Update_ProductDirection(...) によって、行使後に生成される為替決済取引の payer と receiver を反転（買手が基準通貨を支払い、売手が受け取る方向へ変換）します。

ingest-fpml-confirmation-product-fxoption-func.rosetta（L92-L107）& event-common-func.rosetta（L520-L527） 
// 1. 約定時のマッピング：常に Seller = payer, Buyer = receiver として初期化
payerReceiver: MapSellerAsPayerAndBuyerAsReceiver(
            fpmlFxOption -> sellerPartyReference,
            fpmlFxOption -> buyerPartyReference,
            cdmCounterpartyList
        ),
buyerSeller: MapBuyerSeller(
            fpmlFxOption -> buyerPartyReference,
            fpmlFxOption -> sellerPartyReference,
            cdmCounterpartyList
        ),

// 2. 権利行使時（Create_Exercise）：Put オプションなら生成される商品の payer/receiver を反転
alias productWithDirection:
    if optionPayout -> optionType = Put
    then Update_ProductDirection(
                resultProduct,
                optionPayout -> payerReceiver -> payer,
                optionPayout -> payerReceiver -> receiver
            )
    else resultProduct

optionType（OptionTypeEnum）と underlier の決定ルール

金融実務での意味：OptionTypeEnum は PutCallEnum（Put, Call）を継承し、さらに金利・クレジット等のスワップション向けの Payer, Receiver および同一ストライクでコールとプットを同時購入する Straddle を含みます。

為替オプションでの決定ルール：
ストライクレートの分母通貨（基準通貨 perUnitOf）が常に underlier（Cash）になります。買手（buyer）がその基準通貨（perUnitOf）を支払う（Putする）契約（FpMLで strikeQuoteBasis = CallCurrencyPerPutCurrency）なら optionType = Put、買手が基準通貨（perUnitOf）を受け取る（Callする）契約（PutCurrencyPerCallCurrency）なら optionType = Call となります。

product-template-enum.rosetta（L11-L15）& ingest-fpml-confirmation-other-func.rosetta（L2300-L2305） 
enum OptionTypeEnum extends PutCallEnum:
    Payer
    Receiver
    Straddle

// PutCallEnum (base-math-enum or product-common): Put, Call

func MapPutCallEnum:
    inputs: value string (0..1)
    output: result PutCallEnum (0..1)
    set result:
        value switch
            "Put" then Put,
            "CallCurrencyPerPutCurrency" then Put,   // 分母が Put 通貨 → Put
            "Call" then Call,
            "PutCurrencyPerCallCurrency" then Call,  // 分母が Call 通貨 → Call
            default empty

ExerciseTerms（権利行使スタイル・満期日・カットオフ時刻・行使手続）

金融実務での意味：いつ・どのようにオプションを行使できるかを定めます。
・ヨーロピアン（European）：満期日（expirationDate）のカットオフ時刻（expirationTime：NYカット 10:00 USNY や東京カット 15:00 JPTO など）にのみ行使可能。
・アメリカン（American）：行使開始日（commencementDate）から満期日（expirationDate）までの任意の営業日に行使可能。

CDM での制約（condition）：
① style = European のときは commencementDate is absent（開始日を入れてはいけない）。
② style = American のときは commencementDate exists（開始日が必須）かつ expirationDate count = 1。
③ expirationTime を指定するときは expirationTimeType = SpecificTime と相互必須（condition ExpirationTimeChoice）。

product-template-type.rosetta（L720-L771） 
type ExerciseTerms:
    [metadata key]
    style OptionExerciseStyleEnum (0..1)
    commencementDate AdjustableOrRelativeDate (0..1)
    exerciseDates AdjustableOrRelativeDates (0..1)
    expirationDate AdjustableOrRelativeDate (0..*)
    expirationTime BusinessCenterTime (0..1)
    expirationTimeType ExpirationTimeTypeEnum (1..1)
    exerciseProcedure ExerciseProcedure (0..1)
    partialExercise PartialExercise (0..1)
    multipleExercise MultipleExercise (0..1)

    condition AmericanExercise:
        if style = OptionExerciseStyleEnum -> American
        then commencementDate exists
                and exerciseFee is absent
                and partialExercise is absent
                and expirationDate count = 1

    condition EuropeanExercise:
        if style = OptionExerciseStyleEnum -> European
        then expirationDate exists
                and exerciseFeeSchedule is absent
                and multipleExercise is absent
                and latestExerciseTime is absent
                and commencementDate is absent

    condition ExpirationTimeChoice:
        (if expirationTime exists
        then expirationTimeType = ExpirationTimeTypeEnum -> SpecificTime
                and if expirationTimeType = ExpirationTimeTypeEnum -> SpecificTime
                    then expirationTime exists)

6. 実践演習①：実務 為替オプション＆NDO タームシート → CDM マッピング設計チャレンジ

📄 演習対象タームシート：USD/JPY European Vanilla Option（および NDO 拡張）
  • オプション買手（Buyer）：B社（party1 → ロール Party1）
  • オプション売手（Seller）：A銀行（party2 → ロール Party2）
  • 取引内容（権利の方向）：B社（Party1）が 10,000,000 USD を受け取り（Call）、1,500,000,000 JPY を支払う（Put）権利
  • ストライクレート（Strike Rate）：150.00 JPY per USD（分母 perUnitOf = USD、分子 unit = JPY）
  • 権利行使スタイル・満期日・カットオフ：ヨーロピアン（European）、満期日 2026-12-17、東京カット 15:00:00 JPTO（SpecificTime）
  • 受渡決済日（Value Date）：2026-12-21（物理受渡）
