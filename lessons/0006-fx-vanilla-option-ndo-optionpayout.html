為替オプション① 基本構造（FX Vanilla Option / NDO：OptionPayout, BuyerSeller, OptionTypeEnum, ExerciseTerms, OptionStrike）

Lesson 0004〜0005 では、確定した受渡・差金決済義務を表す SettlementPayout を学びました。今回からは、権利の買手（buyer）が行使（Exercise）を選択できる為替オプション（FX Option）に入り、その中核となる OptionPayout の構造を紐解きます。特に「為替のコール／プット（通貨Aのコール＝通貨Bのプット）をCDMはどう正規化するのか？」「buyerSeller と payerReceiver はどう違うのか？」「ストライク価格とオプション料（プレミアム）は PriceQuantity のどこに入るのか？」を一次ソースから解明します。

🎯 このレッスンの到達ゴール（Missionへの接続）

バニラ為替オプション（FX Vanilla Option：ヨーロピアン／アメリカン）および非受渡為替オプション（NDO：Non-Deliverable Option）について、① オプション約定時の OptionPayout が持つ buyerSeller（オプション権利の買手・売手）と payerReceiver（オプション・ペイアウト自体の義務負担者・権利享受者）の意味、および権利行使後に新規生成される為替決済取引（SettlementPayout）における payerReceiver（原資産通貨 underlier の支払者・受取者）への引き継ぎと Put 反転ロジック（Create_Exercise）、② クオート基準（分母通貨 perUnitOf）に基づく optionType（Call / Put）と2通貨数量（quantity vs derivedQuantity）の決定ルール、③ ExerciseTerms・OptionStrike・SettlementTerms（NDOの cashSettlementTerms）、および ④ オプション・プレミアムの表現（transferHistory vs priceQuantity）を一次ソースに基づいて設計・レビューできるようになります。

1. 為替オプションの基本概念と、CDMにおける2つの設計ポイント

まず、為替オプションの金融実務用語と、それをCDM（.rosetta 一次ソース）へマッピングする際の2つのルールを押さえましょう。

  • 為替オプション（FX Vanilla Option / Foreign Exchange Option）：
    将来の特定の期日または期間内に、あらかじめ合意した為替レート（ストライク価格 / 行使価格 / Strike Price）で、一定の2通貨の金額（コール通貨額 Call Currency Amount と プット通貨額 Put Currency Amount）を交換する「権利（義務ではない）」を売買する取引です。権利の買手（buyer）は売手（seller）に対してオプション料（プレミアム / Option Premium）を支払います。
  • NDO（ノン・デリバラブル・オプション / Non-Deliverable Option / 非受渡為替オプション）：
    Lesson 0005 で学んだ NDF のオプション版です。資本規制のある参照通貨（例：BRL、INR、KRW、VEB等）を対象とし、満期日にイン・ザ・マネー（In-the-Money）となって権利行使された場合、2通貨の元本交換は行わず、フィキシング日に観測されたスポットレートとストライク価格の差額（本質的価値 / Intrinsic Value）のみを決済通貨（主に USD）で差金決済します。

設計ポイント①：BuyerSeller と PayerReceiver の同時保持と、オプション約定時・権利行使後のそれぞれで payerReceiver が表す対象

Lesson 0005 の質疑応答でも確認したとおり、CDMには当事者の方向を表す型として BuyerSeller と PayerReceiver が明確に区別されて存在します（base-staticdata-party-type.rosetta:L18-L35）。
OptionPayout（product-template-type.rosetta:L126-L136）は共通基底クラス PayoutBase（product-common-settlement-type.rosetta:L65-L72）を継承（extends PayoutBase）しているため、buyerSeller (1..1) と payerReceiver (1..1) の両方を必須属性として同時に保持します。ここで、「① オプション約定時の OptionPayout -> payerReceiver」と「② 権利行使後に新規生成される為替決済取引の SettlementPayout -> payerReceiver」は、それぞれ表している対象が異なります。

  • OptionPayout -> buyerSeller（BuyerSeller 型）：
    オプション契約（権利という金融商品）の「買手（buyer）」と「売手（seller）」を表します。権利行使を選択できるのは buyer（例：Party1）であり、プレミアムを支払うのも原則として buyer です。また、原資産通貨（underlier）をどちらが受け取る権利か／支払う権利かは、この buyerSeller と optionType（Call / Put）の組み合わせによって表現されます（Call なら buyer が underlier を受け取る権利、Put なら buyer が underlier を支払う権利）。
  • ① オプション約定時の OptionPayout -> payerReceiver が表す対象（「オプション・ペイアウト自体」の義務負担者と権利享受者）：
    OptionPayout -> payerReceiver は、原資産通貨（underlier）の受渡方向を表すものではありません。親クラス PayoutBase の必須属性として、「この OptionPayout（オプションから生じる将来のペイオフ／権利価値）を履行・負担する当事者（payer）と、享受・受け取る当事者（receiver）」を表します。
    オプション取引では、Call であっても Put であっても、権利行使時にペイオフ義務を負うのは常にオプションの売手（seller）であり、権利利益を受け取るのは常にオプションの買手（buyer）です。そのため、一次ソースの FpML 変換関数 MapFxOptionPayout（ingest-fpml-confirmation-product-fxoption-func.rosetta:L92-L107）は、optionType が Call か Put かに関わらず常に MapSellerAsPayerAndBuyerAsReceiver（ingest-fpml-confirmation-party-func.rosetta:L844-L862）を呼び出し、Call でも Put でも機械的に「payer ＝ オプションの seller であった当事者（例：Party2）、receiver ＝ オプションの buyer であった当事者（例：Party1）」をセットします（実際に optionType: "Put" である fx-ex09-euro-opt.json:L28-L31, L42-L45, L50 でも payer: "Party2", receiver: "Party1" となっています）。
  • ② 権利行使イベント実行後に作られる為替決済取引の SettlementPayout -> payerReceiver が表す対象（「原資産通貨 underlier」の支払者と受取者）：
    物理受渡の為替オプションが権利行使されると、一次ソース関数 Create_Exercise（event-common-func.rosetta:L498-L578）によって元のオプション取引は終了し、新たに為替決済取引（SettlementPayout を持つ NonTransferableProduct）が生成されます。
    この新しい為替決済取引はもはやオプションではないため buyerSeller 属性は存在せず、SettlementPayout -> payerReceiver だけが存在し、その payerReceiver は「原資産通貨（underlier ＝ 基準通貨）を実際に支払う当事者（payer）と受け取る当事者（receiver）」を表します。
    たとえばオプション契約で buyer: Party1, seller: Party2（したがって OptionPayout -> payerReceiver は payer: Party2, receiver: Party1）だった場合、Create_Exercise はまず Create_NonTransferableProduct(underlier, optionPayout -> payerReceiver) で OptionPayout -> payerReceiver を新しい SettlementPayout -> payerReceiver にコピーした上で、以下の分岐を行います：
    • 元のオプションが Call（Party1 が原資産通貨 underlier を受け取る権利）だった場合：反転処理は行われず（else resultProduct）、新しい為替決済取引の SettlementPayout -> payerReceiver は payer: Party2, receiver: Party1（Party2 が原資産通貨を支払い、Party1 が原資産通貨を受け取る）となります。
    • 元のオプションが Put（Party1 が原資産通貨 underlier を支払う権利）だった場合：if optionPayout -> optionType = Put then Update_ProductDirection(...)（L520-L527）が呼ばれ、payer と receiver が反転されることにより、新しい為替決済取引の SettlementPayout -> payerReceiver は payer: Party1, receiver: Party2（Party1 が原資産通貨を支払い、Party2 が原資産通貨を受け取る）となります。
      ※一次ソース実装上の補足：Update_ProductDirection（event-common-func.rosetta:L554-L566）は直前の Create_NonTransferableProduct（L575-L577）が生成した SettlementPayout の向きを反転させるために呼ばれていますが、現行の .rosetta コードでは代入先パスが after -> economicTerms -> payout -> OptionPayout -> payerReceiver と記述されており、仕様上の設計意図（Put 行使時に生成される決済商品の payer / receiver 反転）と関数内のパス指定にズレがある点も一次ソースから確認できます。

設計ポイント②：「通貨Aのコール＝通貨Bのプット」を CDM ではどう一意に Call または Put に表現するのか？

為替オプションでは、たとえば「買手（Party1）が 1 AUD = 0.4920 USD のストライクで 75,000,000 AUD を支払い、36,900,000 USD を受け取る権利」は、見方によって「AUD プット」とも「USD コール」とも呼べます。
しかし CDM の OptionPayout -> optionType には Call か Put のどちらか1つしか入りません。CDM における決定ルールは、Lesson 0003〜0005 で貫いてきた「為替レートの分母通貨（基準通貨 perUnitOf）が常に quantity および underlier になる」という不変原則から直接導かれます：

  1. ステップ1（ストライクレートの分母通貨 perUnitOf ＝ underlier & quantity の決定）：
    CDM のストライクレート（OptionPayout -> strike -> strikePrice）では、為替レートの分母通貨（基準通貨 perUnitOf：「1単位あたり」の通貨、例：0.4920 USD per AUD なら AUD、150.00 JPY per USD なら USD）と分子通貨（対価通貨 unit）を指定します。
    不変原則どおり、この分母通貨（基準通貨 perUnitOf）が常にオプションの原資産（underlier ＝ Cash）および priceQuantity -> quantity となり、分子通貨（対価通貨 unit）の金額が price -> derivedQuantity となります。
    ※為替市場では通常、通貨ペアごとにどちらを分母（基準通貨 perUnitOf）にするかのクオート慣行（AUD/USD なら分母は AUD、USD/JPY なら分母は USD）が決まっているため、通貨ペアのクオート方向に従えば perUnitOf（＝underlier & quantity）も一意に定まります。
  2. ステップ2（基準通貨 underlier に対する権利が Call か Put かの決定）：
    原資産（underlier）が分母通貨（基準通貨 perUnitOf）に決まれば、あとはオプションの買手（buyer）がその基準通貨（perUnitOf ＝ underlier）を「受け取る（買う）権利」であれば optionType: "Call"、「支払う（売る）権利」であれば optionType: "Put" に一意に決まります。

💡 補足コラム：FpML の表現（callCurrencyAmount / putCurrencyAmount / strikeQuoteBasis）との違いと Ingest 変換関数

CDM には上記のように perUnitOf・unit と optionType（Call / Put）があり、strikeQuoteBasis という属性は存在しません。一方、一次ソースの FpML 変換関数（ingest-fpml-confirmation-product-fxoption-func.rosetta:L119-L122, L194-L314）を読む際には、FpML 固有の表現方法を知っておく必要があります。

  • FpML での為替オプションの書き方：
    FpML の <fxOption> には optionType（Call / Put）というタグがなく、代わりに「買手が受け取る通貨と金額」を <callCurrencyAmount>、「買手が支払う通貨と金額」を <putCurrencyAmount> として並べて記述します。そしてストライク <strike> には数値 <rate> とともに、「そのレートが Call 通貨と Put 通貨のどちらを分母（1単位あたり）としているか」を示す <strikeQuoteBasis>（CallCurrencyPerPutCurrency または PutCurrencyPerCallCurrency）を記述します。
  • 同じ通貨ペア・同じ市場クオートでも、取引方向によって FpML の strikeQuoteBasis は変わる：
    たとえば USD/JPY（市場クオートは常に JPY per USD＝分母は常に USD）の場合：
    • 買手が USD を受け取り（Call）、JPY を支払う（Put）契約では、分母 USD が CallCurrency、分子 JPY が PutCurrency なので、FpML の strikeQuoteBasis は PutCurrencyPerCallCurrency になります。
    • 買手が USD を支払い（Put）、JPY を受け取る（Call）契約では、分母 USD が PutCurrency、分子 JPY が CallCurrency なので、同じ JPY per USD のレートであっても FpML の strikeQuoteBasis は CallCurrencyPerPutCurrency に変わります。
  • FpML → CDM 変換関数（Ingest）の仕組み：
    変換関数 MapFxOptionPayout / MapFxOptionPriceQuantityList / MapPutCallEnum（ingest-fpml-confirmation-other-func.rosetta:L2300-L2305）は、この FpML の strikeQuoteBasis を見て CDM の構造へ逆算変換しています：
    • strikeQuoteBasis = PutCurrencyPerCallCurrency（分母が CallCurrency）のとき → 分母である callCurrencyAmount の通貨を perUnitOf・underlier・quantity に配置し、買手がその分母通貨を受け取る（Callする）ので optionType = Call に変換する。
    • strikeQuoteBasis = CallCurrencyPerPutCurrency（分母が PutCurrency）のとき → 分母である putCurrencyAmount の通貨を perUnitOf・underlier・quantity に配置し、買手がその分母通貨を支払う（Putする）ので optionType = Put に変換する。

アメリカン・バニラ（fx-ex10）と 非受渡 NDO（fx-ex11）ではどこが変わるのか？

  • アメリカン・オプション（fx-ex10-amer-opt.json:L51-L75）の差分：
    exerciseTerms -> style が "American" になり、権利行使可能期間の開始日を表す commencementDate（例：unadjustedDate: "2001-12-04"）が追加されます。一次ソースの ExerciseTerms（product-template-type.rosetta:L744-L758）には以下の排他制約（condition）が定義されています：
    • condition AmericanExercise：style = American のとき、commencementDate exists（必須）かつ expirationDate count = 1。
    • condition EuropeanExercise：style = European のとき、expirationDate exists かつ commencementDate is absent（設定禁止）、multipleExercise is absent、latestExerciseTime is absent。
  • NDO（非受渡オプション：fx-ex11-non-deliverable-option.json:L36-L86）の差分：
    Lesson 0005 で学んだ「FX Forward に cashSettlementTerms を付けると NDF になる」のと同じ compositional（部品合成）設計です。
    すなわち、OptionPayout -> settlementTerms に settlementType: "Cash"、settlementCurrency: "USD"、そしてフィキシング観測条件を定義した cashSettlementTerms（valuationMethod -> valuationSource、valuationDate -> fxFixingDate、valuationTime）を追加するだけで NDO になります。

3. OptionStrike vs tradeLot -> priceQuantity vs Premium の解説

FX Forward / NDF と FX Option を比較したとき、実務マッピング担当者が疑問に思うのが 「為替オプションには①ストライクレート、②2通貨の名目元本、③約定時スポットレート、④オプション・プレミアム（金額および相場％／pips）があるが、それぞれ OptionPayout と tradeLot -> priceQuantity と transferHistory のどこに入れるのか？」 という点です。一次ソースの変換関数と制約（condition）から4つの核心を整理しましょう。

3-1. ストライクレート（OptionStrike -> strikePrice）と tradeLot -> priceQuantity（2通貨名目元本）の役割分担

FX Forward では約定フォワードレートを tradeLot -> priceQuantity -> price[0] -> value に入れていました。一方、FX Option（fx-ex09 / fx-ex10 / fx-ex11）では、ストライクレート（0.4920 USD/AUD や 1.15 VEB/USD）は OptionPayout -> strike -> strikePrice（Price 型）に格納され、tradeLot -> priceQuantity -> price[0] には value を入れず derivedQuantity（対価通貨の名目元本）のみが格納されます。

なぜかというと、オプションにおいて「ストライク価格（行使価格 K）」は、満期や行使時点でイン・ザ・マネーかアウト・オブ・ザ・マネーかを判定しペイオフを決定するための商品契約上の計算条件（Product -> EconomicTerms -> OptionPayout の構成要素）だからです。

  • OptionPayout -> strike（OptionStrike 型：product-template-type.rosetta:L684-L694）の構造：
    OptionStrike は4属性（strikePrice, strikeReference, referenceSwapCurve, averagingStrikeFeature）の condition: one-of を持ちます。バニラ為替オプションおよび NDO では strikePrice（Price 型）を選び、value（ストライクレート）、perUnitOf（分母通貨＝基準通貨）、unit（分子通貨＝対価通貨）、priceType: "ExchangeRate" を設定します。なお、約定時の参照スポットレートを併記する場合は strikePrice -> composite -> baseValue に格納します（ingest-fpml-confirmation-product-fxoption-func.rosetta:L231-L249）。
  • tradeLot -> priceQuantity[0] における2通貨名目元本の保持とバリデーション：
    基準通貨（perUnitOf）の名目元本は priceQuantity -> quantity（例：75,000,000 AUD）、対価通貨（unit）の名目元本は priceQuantity -> price[0] -> derivedQuantity（例：36,900,000 USD）に配置します。
    ここで PriceSchedule（observable-asset-type.rosetta:L135-L203）は MeasureSchedule（value (0..1) が任意）を継承しているため、price[0] の value と priceType を空（absent）にして derivedQuantity のみを保持することが許容されています。また Lesson 0003 で学んだ三角整合性ルール PriceQuantityTriangulation（observable-common-func.rosetta:L18-L38）も、priceType = CashPrice 等が設定されている場合にのみ発動するため、この構造は CDM のバリデーションを正常に通過します。

3-2. オプション・プレミアム（Option Premium）の CDM における表現

オプションの買手（buyer）から売手（seller）へ支払われる対価であるオプション・プレミアム（Option Premium：例 fx-ex09 の 36,900 USD、決済日 2001-12-06）は、CDM の仕様上、用途に応じて以下の2つの構造で表現できます：

  1. プレミアムの決済キャッシュフロー（「誰から誰へ・いつ・いくら支払うか」という資金移動の記録）：
    TradeState -> transferHistory 内の UnscheduledTransfer（event-common-type.rosetta:L243-L255）として表現します。具体的には以下の属性を設定します（fx-ex09-euro-opt.json:L184-L221）：
    • transferType：UnscheduledTransferEnum -> Premium（product-common-settlement-enum.rosetta:L29："Denotes the amount payable by the buyer to the seller for an option."）
    • quantity および asset：プレミアムの通貨と金額（例：value: 36900, unit.currency: "USD"、asset: Cash (USD)）
    • settlementDate：プレミアムの決済日（例：unadjustedDate: "2001-12-06"、通常は約定日の T+2 営業日）
    • payerReceiver：Product の外側にある実際の決済フローであるため、抽象ロール（Party1/Party2）ではなく PartyReferencePayerReceiver（payerPartyReference: "party1"［買手］、receiverPartyReference: "party2"［売手］）を使用します。
  2. プレミアムの約定単価・料率（「1単位あたりいくらの価格・何％でオプションを売買したか」という取引価格条件）：
    オプション取引自体の約定価格（または一部解約・増額イベント時のフィー単価）を TradeLot 上の価格情報として保持する場合は、tradeLot -> priceQuantity -> price に priceType: PriceTypeEnum -> CashPrice（observable-asset-enum.rosetta:L376-L380, event-common-type.rosetta:L166）を設定した PriceSchedule として表現します（例：1 AUD あたり 0.000492 USD の場合は value: 0.000492, unit.currency: "USD", perUnitOf.currency: "AUD", priceType: "CashPrice"）。
⚠️ 補足コラム：なぜ未決済のプレミアムを transferHistory の UnscheduledTransfer に置くのか？／二次資料との差分と FpML Ingest 仕様
  • 疑問①：フォワードプレミアムなど未決済の将来キャッシュフローなのに、なぜ Product ではなく transferHistory に置くのか？
    旧バージョンの CDM では Product -> EconomicTerms -> Payout 内に Cashflow という型が存在しましたが、現行の CDM では「プレミアムやアップフロント精算金、一部解約手数料などの確定キャッシュフローは、商品の計算ルール（Product）ではなく、取引イベント（約定 Execution 等）に伴って発生した取引固有の資金移動（Transfer）である」という方針に統一され、Product から廃止されました（product-template-type.rosetta:L108 の // Cashflow is no longer part of the product コメント参照）。
    また、transferHistory という属性名は「すでに決済が完了した過去の履歴」のように見えますが、実際には未決済（transferStatus: Pending / Instructed）から決済完了（Settled）までの状態を持つ TransferState（その取引で金額と決済日が確定した全キャッシュフロー）のリストです（event-common-type.rosetta:L204, L243-L248, event-common-enum.rosetta:L66-L72）。そのため、約定時に支払日と金額が合意されたプレミアムは、将来の決済日（settlementDate）を持つ TransferState として約定時点から transferHistory に格納されます。
  • 疑問②：プレミアムは支払日（settlementDate）が決まっているのに、なぜ ScheduledTransfer ではなく UnscheduledTransfer を choice するのか？
    CDM の choice Transfer（event-common-type.rosetta:L249-L265）における Scheduled / Unscheduled / Contingent の3区分は、「支払日が決まっているか否か」による区分ではありません（UnscheduledTransfer も親クラス AssetFlowBase から必須属性 settlementDate (1..1) を継承しています）。その区分基準は「そのキャッシュフローが何から生成されたか」にあります：
    • ScheduledTransfer：金利スワップのクーポン（Coupon / FixedRateReturn / FloatingRateReturn）など、Product -> Payout の定期計算期間スケジュール（CalculationPeriodDates 等）から定期的に算出されるキャッシュフロー（product-common-settlement-enum.rosetta:L10-L20）。
    • UnscheduledTransfer：Payout の定期計算スケジュールから算出されるのではなく、取引イベント（新規約定・増額・一部解約・ノベーション等）に付随して単発（Ad-hoc）で合意・発生するキャッシュフロー（product-common-settlement-enum.rosetta:L21-L32）。Premium（オプション料）、Upfront（スワップの初期精算金）、Termination / PartialTermination（解約精算金）、Novation（更改手数料）はすべてこの UnscheduledTransferEnum に定義されているため、UnscheduledTransfer を選択します。
    • ContingentTransfer：クレジットイベント（CreditEvent）、コーポレートアクション（CorporateAction）、オプション権利行使（Exercise）など、偶発的事象が起きたときにのみ条件付きで生じるキャッシュフロー（product-common-settlement-enum.rosetta:L34-L38）。
  • 二次資料 docs/product-model.md とのギャップ：
    二次資料の common-domain-model/docs/product-model.md（L847-L851）には、「An option trade will contain an instance of a PriceQuantity containing only the premium as price attribute, but no quantity or observable」（オプション取引はプレミアムのみを price に持つ別個の PriceQuantity インスタンスを含む）と記述されています。
    しかし、一次ソースの検証済みJSON（fx-ex09, fx-ex10, fx-ex11, fx-ex20 等すべて）を実際に確認すると、tradeLot -> priceQuantity には原資産2通貨の名目元本用の PriceQuantity が1個だけ存在し、プレミアムは tradeLot -> priceQuantity ではなく、すべて上記①の TradeState -> transferHistory（UnscheduledTransfer, transferType: "Premium"）に出力されています。
  • FpML Ingest 変換関数（MapTransferStateList）の仕様と未実装（TODO）箇所：
    FpML から TradeState へ変換する MapTradeState（ingest-fpml-confirmation-tradestate-func.rosetta:L78-L89）および MapTransferStateList（ingest-fpml-confirmation-payment-func.rosetta:L106-L107, L412-L421）は、FpML の <fxOption> -> <premium> を読み取って transferHistory 内の UnscheduledTransfer（transferType: Premium）へマッピングしています。
    なお、MapFxOptionPremiumListToTransferStateList（L421）のコード末尾には // TODO map other fields というコメントが残されており、FpML の <premium> 内に含まれる <quote>（プレミアムのクオート単価や額面比％）は現行の FpML Ingest 関数ではまだ変換対象になっていません。実務システムでプレミアムの決済キャッシュフローとクオート単価の両方を CDM にマッピングする場合は、本文①（transferHistory）と②（priceQuantity -> price [CashPrice]）を組み合わせて設計します。

3-3. 為替オプションのライフサイクル（全額権利行使・一部権利行使・一部解約・失効）における BusinessEvent -> after と transferHistory の変化

約定した為替オプションが満期または期中に迎えるライフサイクルイベントでは、「① 権利行使（Exercise）か、合意解約（Termination）か」、さらに権利行使の場合は「② 物理受渡（Vanilla Option）か、差金決済（NDO）か」によって、BusinessEvent -> after（TradeState の配列 0..*）の件数と transferHistory の変化が一意に決まります。一次ソースの Create_Exercise（event-common-func.rosetta:L498-L553）およびイベント判定関数 Qualify_Exercise / Qualify_PartialTermination（event-qualification-func.rosetta:L198-L214, L516-L535）に基づいて4つのケースを整理しましょう。

  1. 全額権利行使（Full Exercise：intent = OptionExercise）：
    物理受渡（Vanilla）と差金決済（NDO）で BusinessEvent -> after の構造が異なります：
    • パターンA：物理受渡オプション（FX Vanilla Option）の全額権利行使 → after は 2件（after[0] と after[1]）（event-common-func.rosetta:L548-L552, exercise-swaption-full-physical-func-output.json）
      • after[0]（元のオプション取引）：quantityChange により tradeLot -> priceQuantity の quantity が 0 に減額され、state -> positionState = Closed（closedState -> state = Terminated）となって終了します。この after[0] の transferHistory には新たな Transfer は追加されません（約定時の Premium の履歴がそのまま残るのみです）。なぜなら、物理受渡オプションを行使した直接の結果は「その場でのキャッシュフロー」ではなく「新しい為替決済取引（after[1]）の成立」だからです。
      • after[1]（新規生成される為替決済取引：Replacement Trade）：もはやオプションではなく、原資産通貨（例：Cash: AUD）の SettlementPayout（buyerSeller は存在せず payerReceiver のみを持つ）を格納した新しい TradeState（positionState = Executed）が2件目の after として生成されます。元のオプションの tradeLot -> priceQuantity（75,000,000 AUD と 36,900,000 USD）が引き継がれ（L533）、元のオプションが Call なら payerReceiver は payer: Party2, receiver: Party1、Put なら Update_ProductDirection（L520-L527）によって payer: Party1, receiver: Party2 に反転されます（その後、受渡日が到来した際にこの新取引側で2通貨の受渡決済 Transfer が実行されます）。
    • パターンB：差金決済オプション（NDO）の全額権利行使 → after は 1件（after[0] のみ）（event-qualification-func.rosetta:L208-L209, exercise-cash-settled-func-output.json）
      • NDO（現金決済）では新しい為替決済取引は生成されず、1つの PrimitiveInstruction 内で quantityChange（数量を 0 に更新）と transfer（差金決済金の追加）が同時に実行されます。
      • その結果、単一の after[0]（元のオプション取引）において quantity = 0・positionState = Closed となると同時に、同じ after[0] の transferHistory に差金決済キャッシュフローが ContingentTransfer（transferType: ContingentTransferEnum -> Exercise）として1件追加されます。
  2. 一部権利行使（Partial Exercise：ExerciseTerms -> partialExercise / multipleExercise）：
    アメリカン・オプション等で名目元本の一部（例：75,000,000 AUD のうち 25,000,000 AUD）のみを権利行使した場合も、上記1と同様に物理受渡か差金決済かで一意に決まります：
    • 物理受渡オプションの一部権利行使 → after は 2件（exercise-partial-exercise-func-output.json）：after[0]（元のオプション取引）は残存元本（50,000,000 AUD）に減額された状態でオープン（継続）し、新たな Transfer は追加されません。そして after[1] として、行使された数量分の新規為替決済取引（SettlementPayout）が生成されます。
    • 差金決済オプションの一部権利行使 → after は 1件：after[0]（元のオプション取引）が残存元本に減額されて継続し、同じ after[0] の transferHistory に行使部分の差金決済額が ContingentTransfer（transferType: Exercise）として追加されます。
  3. 一部解約（Partial Termination）および全額解約（Full Termination）と解約手数料（Unwind Fee）：
    満期前に当事者間の合意でオプション契約の一部または全部を解約（Unwind）するイベントは、権利行使（Exercise）とは明確に区別され、Qualify_PartialTermination（event-qualification-func.rosetta:L516-L535）または Qualify_Termination で判定されます（partial-termination-equity-swap-func-input.json:L1-L55）。
    • after の件数は物理受渡・NDO 問わず常に 1件（after[0] のみ）：解約であるため、新しい為替決済取引（SettlementPayout）は生成されません。
    • 元本の減額と解約手数料（時価精算金）の記録：1つの PrimitiveInstruction に quantityChange（direction: Decrease）と transfer を組み合わせて実行します。その結果、after[0]（元のオプション取引）の tradeLot -> priceQuantity が残存元本に減額（全額解約なら 0 かつ Closed）されると同時に、解約に伴って授受される解約手数料（オプションの時価精算金）が、同じ after[0] の transferHistory に UnscheduledTransfer（一部解約なら transferType: UnscheduledTransferEnum -> PartialTermination、全額解約なら transferType: Termination）として追加されます。
  4. アウト・オブ・ザ・マネーでの権利放棄・失効（Expiry / Abandonment）：
    満期日（expirationDate）のカットオフ時刻（expirationTime）にアウト・オブ・ザ・マネーで権利行使されなかった場合、after は 1件（after[0] のみ）です。新規取引や新規 Transfer は一切生成されず、元のオプション取引の quantity が 0、state -> positionState = Closed（closedState -> state = Expired）となって消滅します。

4. 製品分類の自動判定：Qualify_ForeignExchange_VanillaOption vs Qualify_ForeignExchange_NDO

CDM が EconomicTerms の構造からどの為替オプション商品かを自動判定する2つの一次ソース関数（product-qualification-func.rosetta:L1754-L1785）を1行ずつ確認しましょう。

product-qualification-func.rosetta（L1754-L1785）— バニラ為替オプションと NDO の判定ロジック 
// 1. 物理受渡の為替バニラオプション（およびアベレージレート・オプション）の判定
func Qualify_ForeignExchange_VanillaOption:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style <> OptionExerciseStyleEnum -> Bermuda)
            and (optionPayout -> feature is absent
                or optionPayout -> feature -> averagingFeature only exists)
            and optionPayout -> settlementTerms -> cashSettlementTerms is absent

// 2. 非受渡為替オプション（NDO: Non-Deliverable Option）の判定
func Qualify_ForeignExchange_NDO:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style = OptionExerciseStyleEnum -> European)
            and optionPayout -> settlementTerms -> cashSettlementTerms exists

上記2つの一次ソース関数（product-qualification-func.rosetta:L1754-L1785）の判定式から、以下の3つの条件が読み取れます：

  1. バニラオプションと NDO の分岐点は settlementTerms -> cashSettlementTerms の有無：
    Lesson 0005 の「FX Forward vs NDF」と同じく、単一の OptionPayout において settlementTerms -> cashSettlementTerms is absent なら ForeignExchange_VanillaOption、cashSettlementTerms exists（かつ style = European）なら ForeignExchange_NDO と判定されます。
  2. Qualify_ForeignExchange_VanillaOption（L1766-L1768）の行使スタイルと feature 条件：
    ① style <> Bermuda（ヨーロピアンまたはアメリカンのみ）、② feature is absent or feature -> averagingFeature only exists（feature が空であるか、または次回の Lesson 0007 で学ぶアベレージレート条件 averagingFeature のみを持つ場合も ISDA Taxonomy 上 ForeignExchange_VanillaOption に含まれる）という条件になっています。
  3. Qualify_ForeignExchange_NDO（L1783）は European スタイルに限定：
    optionPayout -> exerciseTerms -> style = OptionExerciseStyleEnum -> European が条件として課されています。これは実務上、NDO が満期日の公定フィキシングレート（FxFixingDate）との差額で差金決済されるヨーロピアン型として取引されることに対応しています。

buyerSeller と、約定時・権利行使後のそれぞれで payerReceiver が表す対象

① オプション約定時（OptionPayout 上の buyerSeller と payerReceiver）：
・OptionPayout -> buyerSeller：オプションという「権利」を買った当事者（buyer、例：Party1）と売った当事者（seller、例：Party2）。原資産通貨（underlier）を受け取る権利か支払う権利かは buyerSeller と optionType（Call / Put）の組み合わせで表されます。
・OptionPayout -> payerReceiver：原資産通貨の受渡方向ではなく、「この OptionPayout（オプションのペイオフ義務・権利価値）自体の義務負担者（payer）と権利享受者（receiver）」を表します。そのため MapFxOptionPayout は Call でも Put でも無条件に MapSellerAsPayerAndBuyerAsReceiver を呼び、常に payer: Party2（オプションの売手であった当事者）、receiver: Party1（オプションの買手であった当事者）をセットします。

② 権利行使イベント実行後（新規生成される為替決済取引 SettlementPayout -> payerReceiver）：
権利行使関数 Create_Exercise によって生成される為替決済取引（SettlementPayout）はもはやオプションではないため buyerSeller を持たず、SettlementPayout -> payerReceiver は「原資産通貨（underlier ＝ 基準通貨）を実際に支払う当事者（payer）と受け取る当事者（receiver）」を表します。
・元のオプションが Call のとき：反転せず、SettlementPayout -> payerReceiver は payer: Party2, receiver: Party1（Party2 が原資産通貨を支払い、Party1 が受け取る）。
・元のオプションが Put のとき：if optionPayout -> optionType = Put then Update_ProductDirection(...) により反転され、SettlementPayout -> payerReceiver は payer: Party1, receiver: Party2（Party1 が原資産通貨を支払い、Party2 が受け取る）となります。

金融実務での意味：OptionTypeEnum は PutCallEnum（Put, Call）を継承し、さらに金利・クレジット等のスワップション向けの Payer, Receiver および同一ストライクでコールとプットを同時購入する Straddle を含みます。

CDM の為替オプションでの決定ルール：
ストライクレート（strike -> strikePrice）の分母通貨（基準通貨 perUnitOf）が常に underlier（Cash）および priceQuantity -> quantity になります。そして、買手（buyer）がその基準通貨（perUnitOf ＝ underlier）を受け取る権利なら optionType = Call、買手がその基準通貨（perUnitOf ＝ underlier）を支払う権利なら optionType = Put となります。

ExerciseTerms（権利行使スタイル・満期日・カットオフ時刻・行使手続）

金融実務での意味：いつ・どのようにオプションを行使できるかを定めます。
・ヨーロピアン（European）：満期日（expirationDate）のカットオフ時刻（expirationTime：NYカット 10:00 USNY や東京カット 15:00 JPTO など）にのみ行使可能。
・アメリカン（American）：行使開始日（commencementDate）から満期日（expirationDate）までの任意の営業日に行使可能。

CDM での制約（condition）：
① style = European のときは commencementDate is absent（開始日を入れてはいけない）。
② style = American のときは commencementDate exists（開始日が必須）かつ expirationDate count = 1。
③ expirationTime を指定するときは expirationTimeType = SpecificTime と相互必須（condition ExpirationTimeChoice）。
