Phase 3 · Lesson 0008 · Synthetic Multi-Forward & Multi-Leg FX Option Strategy

シンセティック・マルチフォワードの複合マッピング設計（Call＋Put の合成フォワード × 複数期日 CalculationSchedule / 複数 OptionPayout の設計比較と Qualification 関数の挙動）

Phase 3（為替デリバティブ各論）の総仕上げとして、実務の対顧客為替ヘッジで広く組成されるシンセティック・マルチフォワード（Synthetic Multi-Forward：Call オプションと Put オプションを組み合わせた合成先渡 × 複数期日スケジュール）を題材に、CDM の一次ソース（product-template-type.rosetta、observable-asset-type.rosetta、product-qualification-func.rosetta、event-common-type.rosetta）の型制約に適合するデータマッピング設計を整理します。

🎯 このレッスンの到達ゴール（Missionへの接続）

① シンセティック・フォワード（Call＋Put の合成先渡）における Call レッグと Put レッグの buyerSeller・約定時の OptionPayout -> payerReceiver・権利行使後の為替決済取引 SettlementPayout -> payerReceiver の対応関係を正確に跡付け、② 複数期日（マルチフォワード）を表現する3つの設計パターン（単一 Trade 内の複数 OptionPayout 展開、CalculationSchedule / datedValue による集約、packageReference によるパッケージ取引分割）を .rosetta の型制約（Price -> condition AmountOnlyExists 等）に基づいて比較・選択でき、③ 複数 OptionPayout 構成時における Qualify_* 関数の only-element 判定挙動と、対になる tradeLot -> priceQuantity（@key:scoped ↔ @ref:scoped）の設計・検証を独力で遂行できるようになります。

1. シンセティック・マルチフォワードの金融実務構造と方向属性（buyerSeller vs payerReceiver）

まず、為替デリバティブ実務におけるシンセティック・フォワード（Synthetic Forward / 合成先渡）およびシンセティック・マルチフォワード（Synthetic Multi-Forward / 複数期日合成先渡）の仕組みを確認し、これまで学んだ CDM の方向属性ルールが複合オプション戦略でどのように機能するかを整理します。

1-1. シンセティック・フォワードとマルチフォワードの実務バリエーション

為替のシンセティック・フォワードとは、同一通貨ペア・同一満期日（Expiration Date）・同一決済日（Value Date）について、一方の当事者が Call オプションの買手（buyer）になると同時に Put オプションの売手（seller）になることで、為替予約（FX Forward）と同等の損益・受渡プロファイルを合成するオプション戦略です。
輸出入企業の継続的な実需ヘッジでは、この Call＋Put のペアを月次や四半期などの複数期日（T1, T2, …, TN）にわたるストリップ（スケジュール）として1本のタームシートに束ねたシンセティック・マルチフォワードが頻繁に用いられます。条件の付け方により、実務上は以下のバリエーションが存在します。

実務類型（日 / 英） 契約条件の特徴（顧客 Party1 が各期日に基準通貨 USD を受け取り対価通貨 JPY を支払う例） CDM マッピング設計上の着眼点
① フラット合成マルチフォワード
（Symmetric Synthetic Multi-Forward）		 全期日 T1 … TN において、Call レッグと Put レッグのストライクレート K が同一（例：全期日 148.00 JPY per USD）かつ名目元本も同一（例：各期日 1,000,000 USD）。
満期レート STi > K なら顧客が Call を行使し、STi < K なら銀行が Put を行使するため、いずれのケースでもレート K で 1,000,000 USD と 148,000,000 JPY を交換する。 		同一期日内では Call レッグと Put レッグの基準通貨数量（quantity）および対価通貨数量（derivedQuantity）が一致する。ただし Call と Put で buyerSeller と payerReceiver が逆転する。
② ステップ・ストライク型 / レンジ・フォワード
（Step-Strike / Risk Reversal Collar Strip）		 ・ステップ・ストライク：期日ごとにストライクレートが段階的に変化する（例：T1 は 149.00、T2 は 147.00、T3 は 145.00 JPY per USD）。
・レンジ・フォワード（リスクリバーサル）：同一期日内で Call ストライク Kcall（例：上限 150.00）と Put ストライク Kput（例：下限 145.00）に幅を持たせる。 		期日ごと、あるいは同一期日の Call と Put の間でストライクレート K と対価通貨金額（derivedQuantity = quantity × K）が異なるため、それぞれ個別の OptionStrike と PriceQuantity が必要になる。
③ レシオ・マルチフォワード / ノックアウト付
（Ratio / Barrier Enhanced Multi-Forward）		 ・レシオ（Ratio 1:2 等）：顧客が買手となる Call レッグの元本を 1,000,000 USD、顧客が売手となる Put レッグの元本を2倍の 2,000,000 USD とすることで、ストライクレートを市場フォワードより顧客有利に設定する。
・バリア付：各期日のレッグにノックアウト・バリア（Barrier -> knockOut）を付与する。 		同一期日内でも Call レッグと Put レッグで基準通貨数量（quantity）自体が異なるため、Call 用と Put 用で独立した PriceQuantity インスタンスを定義して @ref:scoped で結ぶ必要がある。

1-2. 推奨される基本表現：Call 用と Put 用の2つの OptionPayout 分離と方向属性（buyerSeller vs payerReceiver）の整合性

シンセティック・フォワードの1期日分（Call 買い＋Put 売りのペア）を CDM で表現する場合、EconomicTerms -> payout (1..*)（product-template-type.rosetta:L45）の配列内に、Call レッグ用の OptionPayout と Put レッグ用の OptionPayout を別々の要素として並べる構成が基本となります。

💡 補足コラム：なぜ optionType: Straddle や StrategyFeature で1つの OptionPayout にまとめないのか？

CDM の OptionPayout（product-template-type.rosetta:L126-L135）には、optionType の列挙値として Straddle（product-template-enum.rosetta:L11-L15）があり、また feature -> strategyFeature として StrategyFeature（strikeSpread / calendarSpread、product-template-type.rosetta:L710-L718）も定義されています。しかし、これらを用いてシンセティック・フォワードの Call と Put を1つの OptionPayout に集約しようとすると、以下の型構造上の不整合が生じます。

product-template-type.rosetta（L126-L135, L710-L718）— OptionPayout の単一 buyerSeller と StrategyFeature 
type OptionPayout extends PayoutBase:
    buyerSeller BuyerSeller (1..1) // 1つの OptionPayout につき buyer と seller の組は1つだけ
    feature OptionFeature (0..1)
    ...
    optionType OptionTypeEnum (0..1) <"... Straddle is used for the case of straddle strategy, that combine a call and a put with the same strike.">

type StrategyFeature:
    strikeSpread StrikeSpread (0..1)      // upperStrike (1..1), upperStrikeNumberOfOptions (1..1)
    calendarSpread CalendarSpread (0..1)  // expirationDateTwo (1..1)
  • optionType: Straddle との違い：ストラドルは「同一当事者が同一ストライクの Call と Put の両方を買う（または両方を売る）」取引であるため、単一の buyerSeller（例：buyer: Party1, seller: Party2）で表せます。一方、シンセティック・フォワードは「一方の当事者が Call を買い（buyer: Party1, seller: Party2）、同時に Put を売る（buyer: Party2, seller: Party1）」取引です。1つの OptionPayout は buyerSeller (1..1) を1組しか持てないため、売買方向が逆転する Call と Put は別々の OptionPayout に分ける必要があります。
  • StrategyFeature（StrikeSpread / CalendarSpread）の用途：StrikeSpread は2つのストライクを持つ垂直スプレッドの上限ストライク（upperStrike）を、CalendarSpread は2つの満期日を持つカレンダー・スプレッドの第2満期日（expirationDateTwo）を補足する型であり、Call と Put の買手・売手逆転や3期日以上のストリップを表現するものではありません。

2. シンセティック・マルチフォワードの3つのマッピング設計パターンと .rosetta 型制約の検証

複数期日（N 期日）のシンセティック・マルチフォワードを CDM で表現する場合、一次ソースの型定義に照らして3つの設計パターン（パターンA・パターンB・パターンC）が候補となります。それぞれの構造と、.rosetta の制約条件（condition）から導かれる適用可否を比較しましょう。

2-1. パターンA：単一 Trade 内の EconomicTerms -> payout (1..*) に 2N 個の OptionPayout を展開する設計

EconomicTerms -> payout はカーディナリティ (1..*)（product-template-type.rosetta:L45）を持ち、対応する TradeLot -> priceQuantity も (1..*)（product-template-type.rosetta:L319）を持ちます。
したがって、N 期日（例：3期日 T1, T2, T3）× 各期日の Call レッグ・Put レッグ ＝ 計 2N 個（例：6個）の OptionPayout を economicTerms -> payout 配列に並べる設計がパターンAです。

  • 期日別・レッグ別の条件を個別に表現可能：各 OptionPayout が自身の exerciseTerms -> expirationDate、settlementTerms -> settlementDate -> valueDate、strike -> strikePrice、feature -> barrier、および priceQuantity 参照（@ref:scoped）を独立して持つため、ステップ・ストライク（期日別ストライク）、レンジ・フォワード（Call/Put 別ストライク）、レシオ・フォワード（Call/Put 別数量）、期日別バリアのいずれにも型制約違反なく対応できます。
  • 期日別・レッグ別の権利行使（ExerciseInstruction）に対応：OptionPayout は PayoutBase から [metadata key]（product-common-settlement-type.rosetta:L66）を継承しているため、各 OptionPayout に一意の @key（例："opt-t1-call", "opt-t1-put" 等）を付与できます。各期日の満期時には、ExerciseInstruction -> exerciseOption（[metadata reference]、event-common-type.rosetta:L132-L133）で行使対象の OptionPayout を個別に指定できます。

2-2. パターンB：Call 1個＋Put 1個の計2個の OptionPayout に集約し、CalculationSchedule や datedValue を使う設計の検証

「期日ごとに OptionPayout を分けず、Call 用 OptionPayout 1個と Put 用 OptionPayout 1個の計2個だけを定義し、その内部の schedule: CalculationSchedule (0..1) や PriceQuantity の datedValue で複数期日を表せないか？」という設計案がパターンBです。
ここで一次ソース（product-template-type.rosetta および observable-asset-type.rosetta）の型定義と condition を確認すると、パターンBには明確な構造上の制約があることが分かります。

product-template-type.rosetta（L461-L468, L684-L694）& observable-asset-type.rosetta（L204-L207） 
// 1. CalculationSchedule と SchedulePeriod の定義（product-template-type.rosetta:L461-L468）
type CalculationSchedule:
    schedulePeriod SchedulePeriod (1..*) <"Defines a period of a calculation schedule structure.">

type SchedulePeriod:
    calculationPeriod DateRange (1..1) <"Period for which the payment is generated.">
    paymentDate date (1..1) <"Adjusted payment date.">
    fixingPeriod DateRange (1..1) <"Period over which the underlying price is observed.">
    deliveryPeriod CalculationScheduleDeliveryPeriods (0..1) <"Period and time profile over which the delivery takes place.">

// 2. OptionStrike -> strikePrice の型は PriceSchedule ではなく Price（product-template-type.rosetta:L684-L686）
type OptionStrike:
    strikePrice Price (0..1) <"Defines the strike of an option in the form of a price...">
    ...

// 3. Price 型は datedValue（日付別ステップ値）を禁止している（observable-asset-type.rosetta:L204-L207）
type Price extends PriceSchedule:
    condition AmountOnlyExists: <"The amount must exist when the price represents a single value, and steps must be absent.">
        value exists and datedValue is absent

この一次ソース定義から、パターンBの適用限界として以下の3点が導かれます。

  1. 制約①：OptionStrike -> strikePrice は Price 型であり、期日別ステップ・ストライク（datedValue）を持てない：
    tradeLot -> priceQuantity -> quantity（NonNegativeQuantitySchedule 型）や price（PriceSchedule 型）は Schedule を継承しているため datedValue: NonNegativeDatedValue (0..*)（日付 date と値 value のペア配列、base-math-type.rosetta:L54, L65, L79-L86）を持てます。
    しかし、OptionPayout -> strike -> strikePrice は PriceSchedule を特殊化した Price 型であり、condition AmountOnlyExists（observable-asset-type.rosetta:L206-L207）によって value exists and datedValue is absent（単一の value のみ必須、datedValue は禁止）と定められています。したがって、期日ごとにストライクレートが異なるステップ・ストライク型マルチフォワードは、1つの OptionPayout（パターンB）では表現できず、期日ごとに OptionPayout を分けるパターンA（またはパターンC）が必須となります。
  2. 制約②：CalculationSchedule -> schedulePeriod が持つ属性の範囲：
    SchedulePeriod（product-template-type.rosetta:L464-L468）は、各期の計算期間（calculationPeriod: DateRange）、決済日（paymentDate: date）、フィキシング観測期間（fixingPeriod: DateRange）、受渡期間プロファイル（deliveryPeriod）を非パラメトリックに列挙する構造です。そのため、全期日で単一のストライクレート K を共有するフラットなマルチフォワードにおいて、各期の観測期間（fixingPeriod）と決済日（paymentDate）を明示する補助スケジュールとしては機能しますが、期日別のストライクや期日別のノックアウト条件を格納する場所は持っていません。
  3. 制約③：ExerciseTerms における複数満期日の表現：
    1つの OptionPayout 内で複数の権利行使日を表す場合、ExerciseTerms -> expirationDate (0..*) に複数の満期日を列挙する（condition EuropeanExercise は expirationDate exists のみを要求し、AmericanExercise と異なり count = 1 制約を持たない、product-template-type.rosetta:L751-L757）か、または style: Bermuda ＋ exerciseDates ＋ multipleExercise（L759-L764）を使用することになります。ただしその場合、各期日の権利行使はすべて同一の OptionPayout に対する部分行使（Partial / Multiple Exercise）として処理する必要があります。

2-3. パターンC：各レッグ（または各期日）を独立した複数の Trade に分け、packageReference（IdentifiedList）で束ねる設計

実務において「顧客向けのタームシートは1枚のパッケージ契約だが、取引管理システムや取引情報蓄積機関（Trade Repository）への報告上は各期日の Call オプション・Put オプションに個別の UTI/USI（取引識別子）を採番して独立した Trade（TradeState）として管理する」というケースがあります（実際、FpML の fx-ex25-option-strategyComponentIdentifier.xml でも、ストラドルの Option1 と Option2 に別々の UTI/USI ...913 と ...914 が割り当てられています）。
CDM では、複数の独立した Trade を1つのパッケージ取引として紐づけるために、IdentifiedList 型を用いたパッケージ参照メカニズム（base-staticdata-identifier-type.rosetta:L28-L33、event-common-type.rosetta:L316-L318, L497、event-workflow-type.rosetta:L80）が用意されています。

base-staticdata-identifier-type.rosetta（L28-L33）& event-common-type.rosetta（L316-L318, L492-L497） 
type IdentifiedList: <"Attaches an identifier to a collection of objects... One use case is the representation of package transactions, where each component is a separate trade with its own identifier, and those trades are linked together as a package with its own identifier.">
    [metadata key]
    listId Identifier (1..1) <"The identifier for the list. In the case of a package transaction, this would be the package identifier.">
    componentId Identifier (2..*) <"Identifiers for each component of the list. Since the data type is used to link multiple identified objects together, at least 2 components are required in the list.">
    price Price (0..1) <"The price of the package.">

type ExecutionDetails:
    [metadata key]
    executionType ExecutionTypeEnum (1..1)
    executionVenue LegalEntity (0..1)
    packageReference IdentifiedList (0..1) <"A reference to the package linking the trade with other trades, in case the trade was executed as part of a package...">

// Trade 型のパッケージ整合性制約（event-common-type.rosetta:L316-L318）
condition PackageTrade: <"When the trade is part of a package as specified in the execution details, the trade identifier must be found as one of the package components.">
    if executionDetails -> packageReference exists
    then executionDetails -> packageReference -> componentId -> assignedIdentifier contains tradeIdentifier -> assignedIdentifier

パターンCで設計する際は、以下の2つの一次ソース制約を守る必要があります。

  • componentId の最小カーディナリティ (2..*)：IdentifiedList -> componentId には少なくとも2件以上の構成取引IDを列挙しなければなりません。
  • Trade -> condition PackageTrade（event-common-type.rosetta:L316-L318）：各構成 Trade が保持する executionDetails -> packageReference -> componentId -> assignedIdentifier のリストの中に、その Trade 自身の tradeIdentifier -> assignedIdentifier が必ず含まれていなければなりません。また、約定イベント（BusinessEvent）レベルでは EventInstruction -> packageInformation: IdentifiedList (0..1)（event-workflow-type.rosetta:L80）にパッケージ全体情報を1回記録できます。

2-4. 3つのマッピング設計パターンの比較まとめ

3. 複数 OptionPayout に対する Qualification 関数（Qualify_*）の挙動と NonTransferableProduct の分類設計

上の比較表の4行目で触れたとおり、単一 Trade の EconomicTerms -> payout に2個以上の OptionPayout を格納した場合（パターンAおよびパターンB）、CDM の為替プロダクト自動判定関数（Qualify_*）がどのように動作するかを一次ソース（product-qualification-func.rosetta）で検証します。

3-1. only-element 演算子による判定挙動（SettlementPayout との非対称性）

product-qualification-func.rosetta における Qualify_AssetClass_ForeignExchange（L143-L176）、Qualify_ForeignExchange_VanillaOption（L1754-L1769）、および Qualify_ForeignExchange_NDO（L1771-L1785）の定義を確認しましょう。

product-qualification-func.rosetta（L143-L176, L1754-L1785, L1981-L2026）— only-element の挙動 
func Qualify_AssetClass_ForeignExchange:
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)

    // 【重要】OptionPayout に対して only-element（要素が厳密に1個のときのみ値を返し、2個以上なら empty を返す）を使用
    alias optionUnderlier: economicTerms -> payout as OptionPayout only-element -> underlier
    // 一方、SettlementPayout に対しては only-element を使わず全要素のリストとして抽出している
    alias settlementUnderliers: economicTerms -> payout as SettlementPayout -> underlier

    set is_product:
        (SettlementPayoutOnlyExists(economicTerms -> payout)
                and (settlementUnderliers extract [ item as Cash exists ] all = True ...))
            or ...
            or (economicTerms -> payout only-element as OptionPayout exists
                and (optionUnderlier as Cash exists ...))

func Qualify_ForeignExchange_VanillaOption:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style <> OptionExerciseStyleEnum -> Bermuda)
            and (optionPayout -> feature is absent
                or optionPayout -> feature -> averagingFeature only exists)
            and optionPayout -> settlementTerms -> cashSettlementTerms is absent

func Qualify_ForeignExchange_NDO:
    [qualification Product]
    inputs: economicTerms EconomicTerms (1..1)
    output: is_product boolean (1..1)
    alias optionPayout: economicTerms -> payout only-element as OptionPayout
    set is_product:
        Qualify_AssetClass_ForeignExchange(economicTerms)
            and optionPayout exists
            and (optionPayout -> exerciseTerms -> style = OptionExerciseStyleEnum -> European)
            and optionPayout -> settlementTerms -> cashSettlementTerms exists

Rune DSL 読解ガイドで確認したとおり、only-element 演算子は「対象のリストの要素数がちょうど1個のときだけその要素を評価し、要素数が0個または2個以上のときは空（empty / absent）と評価する」演算子です。
そのため、SettlementPayout を2個持つ FX Swap や NDS は SettlementPayoutOnlyExists と count = 2 によって Qualify_AssetClass_ForeignExchange = True かつ Qualify_ForeignExchange_Swap / NDS = True と判定されるのに対し、OptionPayout を2個以上持つ取引（1期日のシンセティック・フォワード、ストラドル、あるいは 2N 個の OptionPayout を持つシンセティック・マルチフォワード）では、economicTerms -> payout only-element as OptionPayout が empty となるため、Qualify_AssetClass_ForeignExchange・Qualify_ForeignExchange_VanillaOption・Qualify_ForeignExchange_NDO のすべてが False を返します（同ファイル L2017 にヘルパー関数 OptionPayoutOnlyExists は定義されていますが、現行の Qualify_AssetClass_ForeignExchange では使われておらず、複数 OptionPayout から成る為替オプション戦略用の Qualify_ForeignExchange_* 関数も未定義です）。

3-2. 単一 Trade 設計（パターンA・B）における NonTransferableProduct -> taxonomy と condition PrimaryAssetClass

パターンAやパターンBのように単一 Trade 内に複数の OptionPayout を格納する場合、Qualify_* 関数による自動分類（calculated: true の ISDA Taxonomy 付与）が行われないため、NonTransferableProduct -> taxonomy に明示的な商品分類（ProductTaxonomy）を設定しておくのが実務上の推奨設計となります。
また、非標準的な複合条件を含む取引であることを示すフラグ economicTerms -> nonStandardisedTerms: true を設定する場合、NonTransferableProduct（product-template-type.rosetta:L307-L315）の以下の制約が発火することに注意してください。

product-template-type.rosetta（L307-L315）— condition PrimaryAssetClass 
type NonTransferableProduct:
    [metadata key]
    identifier ProductIdentifier (0..*)
    taxonomy ProductTaxonomy (0..*)
    economicTerms EconomicTerms (1..1)

    condition PrimaryAssetClass: <"Specifies that when nonStandardisedTerms are True that a primary asset class must be specified.">
        if economicTerms -> nonStandardisedTerms = True
        then taxonomy -> primaryAssetClass exists

つまり、economicTerms -> nonStandardisedTerms: true を設定したときは、必ず product -> taxonomy に primaryAssetClass: { "@data": "ForeignExchange" }（AssetClassEnum -> ForeignExchange）を含めなければバリデーションエラーとなります。

⚠️ FpML Ingest 関数における <strategy> および <fxFlexibleForward> の未実装ギャップ（一次ソース確認）

CDM のスキーマ（product-template-type.rosetta）自体は EconomicTerms -> payout (1..*) による複数 OptionPayout 格納や CalculationSchedule を備えていますが、FpML から CDM への変換関数（ingest-fpml-confirmation-tradestate-func.rosetta:L256-L358, L417-L450 の MapNonTransferableProduct および MapPriceQuantityList）を確認すると、fpmlTrade -> product switch の分岐リストに FpML の複合戦略要素 fpml.Strategy（例：fx-ex23-straddle.xml、fx-ex25-option-strategyComponentIdentifier.xml）および期間内分割実行フォワード要素 fpml.FxFlexibleForward（例：fx-ex27-flexible-term-forward.xml）が含まれていません。
そのため、これらの FpML サンプルを Ingest 関数に通したテスト出力（fpml-5-13-incomplete-products-fx-derivatives/fx-ex23-straddle.json、fx-ex25-option-strategyComponentIdentifier.json、fx-ex27-flexible-term-forward.json）では、default 分岐に入って product と tradeLot が空になり、tradeIdentifier・tradeDate・party のみが出力されています。実務でシンセティック・マルチフォワードやオプション・ストラテジーを CDM にマッピングする際は、FpML Ingest 関数のデフォルト出力に依存せず、本レッスンで整理する正規スキーマ構造（パターンAまたはパターンC）を直接構築してください。

4. tradeLot -> priceQuantity の複合マッピング設計とライフサイクル変化

続いて、Product -> economicTerms -> payout と対になる tradeLot -> priceQuantity の設計ルールを確認します。複合為替デリバティブであっても、Lesson 0003〜Lesson 0007 で確立した基本原則はそのまま貫かれます。

4-1. クオート基準不変原則と複数 PriceQuantity のスコープ参照（@key:scoped ↔ @ref:scoped）

  1. クオート基準不変原則の維持：
    各レッグのストライクレート OptionStrike -> strikePrice のクオート基準が JPY per USD（分母＝基準通貨 perUnitOf = USD、分子＝対価通貨 unit = JPY）である場合、Call レッグでも Put レッグでも、常に分母（基準通貨 USD）の名目元本が priceQuantity -> quantity（および OptionPayout -> underlier の Cash: USD）に配置され、分子（対価通貨 JPY）の交換金額（quantity × K）が priceQuantity -> price -> derivedQuantity に配置されます。
  2. 1 OptionPayout : 1 PriceQuantity の分離結線（パターンAにおける推奨設計）：
    単一 Trade 内に 2N 個の OptionPayout を並べるパターンAでは、tradeLot[0] -> priceQuantity 配列にも各レッグに対応する PriceQuantity を並べ、@key:scoped と @ref:scoped で結びます。
    特に、レシオ・マルチフォワード（例：期日 T1 の Call レッグは元本 1,000,000 USD、Put レッグは元本2倍の 2,000,000 USD）や、レンジ・フォワード／リスクリバーサル（例：Call ストライク Kcall = 150.00 で derivedQuantity = 150,000,000 JPY、Put ストライク Kput = 145.00 で derivedQuantity = 290,000,000 JPY）では、同一期日内でも Call と Put で quantity や derivedQuantity が異なるため、各 OptionPayout ごとに独立した PriceQuantity（quantity-1〜quantity-2N）を1対1で割り当てる設計が適しています。
    （なお、全レッグではなく「同一期日の Call と Put が同一元本・同一ストライク」であるフラット合成フォワードに限り、期日ごとに1つの PriceQuantity を定義して同一期日の Call と Put の両方の OptionPayout -> priceQuantity -> quantitySchedule から同じ @ref:scoped を共有参照することも文法上は可能ですが、満期時に片方が行使・他方が消滅する際の個別数量管理を考慮すると、レッグ別に PriceQuantity を分けておく方が見通しが良くなります）。
  3. ゼロコスト（Zero-Cost） vs ネット・プレミアム決済と対顧客マージン：
    シンセティック・マルチフォワードは、顧客の初期プレミアム支払をゼロにするゼロコスト（Zero-Cost）で組成されることが一般的です（銀行側の対顧客マージンはストライクレート K の水準、または Call/Put のレシオ比率に織り込まれます）。この場合、プレミアム用の TransferState は不要です。
    一方、約定時にネット・プレミアム（一括または期日・レッグ別）の授受が発生する契約では、Lesson 0006 と同様に TradeState -> transferHistory に UnscheduledTransfer（transferType: "Premium"、PartyReferencePayerReceiver 使用）を追加し、単価や料率を記録する場合は該当する PriceQuantity -> price に priceType: "CashPrice"（必要に応じ理論値 baseValue ＋ マージン operand の PriceComposite）を併記します。

各期日の Put レッグ（OptionPayout：顧客が売手・銀行が買手）

金融実務での意味：各期日 Ti の満期時スポットレート STi がストライク Ki を下回った（STi < Ki）ときに、買手である銀行（Party2）が権利行使して基準通貨 USD を顧客（Party1）へレート Ki で支払い（売り渡し）、顧客が USD を受け取って JPY を支払うプット・オプションです。

CDM での役割：銀行が買手・顧客が売手であるため、buyerSeller: { buyer: Party2, seller: Party1 } となり、約定時の OptionPayout -> payerReceiver は売手＝義務負担者の原則に従い { payer: Party1, receiver: Party2 } となります。そして満期に銀行がこの Put を行使（Create_Exercise）すると、optionType = Put により Update_ProductDirection で方向が反転され、成立する為替決済取引（SettlementPayout）の payerReceiver は Call 行使時と同じ { payer: Party2, receiver: Party1 }（銀行が USD を支払い、顧客が USD を受け取る）になります。
